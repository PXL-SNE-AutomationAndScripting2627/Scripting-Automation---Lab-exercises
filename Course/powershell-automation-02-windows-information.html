Collecting Windows information

02 - Windows information

Originele pagina openen →

Administrators often need a consistent inventory of operating systems, hardware, storage, processes, accounts, and network adapters. PowerShell exposes this information as objects that can be filtered, combined, and exported.

Learning objectives

By the end of this lesson, you can:

  • retrieve a consolidated Windows overview with Get-ComputerInfo;
  • explain CIM classes, instances, properties, and methods;
  • discover CIM classes and query selected instances efficiently;
  • collect operating-system, processor, BIOS, disk, memory, process, account, and adapter data; and
  • build one structured inventory object for reporting.

Prerequisites

  • Complete the PowerShell Basics course and the local-user automation lesson.
  • Use PowerShell on Windows; the CIM cmdlets and classes in this lesson are Windows-specific.
  • No administrator rights are required for most read-only examples, although some properties may be restricted.

Start with Get-ComputerInfo

Get-ComputerInfo combines many operating-system and hardware properties into one object.

Get-ComputerInfo |
    Select-Object CsName, WindowsProductName, WindowsVersion,
        OsArchitecture, CsTotalPhysicalMemory, BiosSerialNumber

It is convenient for an overview, but CIM queries give more control over which class and properties are retrieved.

Understand CIM

The Common Information Model (CIM) describes manageable hardware and software consistently:

  • a namespace groups related management classes;
  • a class describes a type of resource, such as Win32_OperatingSystem;
  • an instance represents one actual resource on a computer;
  • a property stores information about an instance; and
  • a method represents an action supported by a class or instance.

CIM hierarchy

flowchart LR
    A["Namespace: groups classes"] --> B["Class: Win32_OperatingSystem"]
    B --> C["Instance: one operating system"]
    C --> D["Property: Caption or Version"]
    C --> E["Method: an available action"]

Inspect methods before using them: unlike querying properties, a method can change system state.

Prefer CIM cmdlets to the retired Get-WmiObject family. CIM cmdlets support current PowerShell and can use WS-Management for remote operations.

Discover classes before querying

Get-CimClass -ClassName 'Win32_*OperatingSystem*' |
    Select-Object CimClassName

Get-CimClass -ClassName Win32_Service |
    Select-Object -ExpandProperty CimClassMethods

Get-Help Get-CimInstance -Examples

Tab completion can help with class names after -ClassName. Use Get-CimClass when you need broader discovery.

Query operating-system and hardware classes

$operatingSystem = Get-CimInstance -ClassName Win32_OperatingSystem
$computerSystem = Get-CimInstance -ClassName Win32_ComputerSystem
$processor = Get-CimInstance -ClassName Win32_Processor |
    Select-Object -First 1
$bios = Get-CimInstance -ClassName Win32_BIOS
$baseboard = Get-CimInstance -ClassName Win32_BaseBoard |
    Select-Object -First 1

$operatingSystem |
    Select-Object Caption, Version, OSArchitecture, LastBootUpTime

$processor |
    Select-Object Name, NumberOfCores, NumberOfLogicalProcessors

$bios |
    Select-Object Manufacturer, SMBIOSBIOSVersion, SerialNumber

Query only the classes and properties required by the report. Collecting everything is slower and makes later code harder to understand.

Filter at the CIM provider

-Filter uses WMI Query Language syntax and can reduce the amount of data returned.

Get-CimInstance -ClassName Win32_Process -Filter "Name LIKE 'P%'" |
    Select-Object Name, ProcessId, WorkingSetSize

Use Where-Object when filtering an existing collection or when the provider cannot express the condition. Use -Filter when the CIM provider can do the work before returning objects.

Discover CIM methods before using them

Methods perform actions rather than only returning state. Inspect the class metadata and documentation before calling one.

Get-CimClass -ClassName Win32_Service |
    Select-Object -ExpandProperty CimClassMethods

Get-CimClass -ClassName Win32_Process |
    Select-Object -ExpandProperty CimClassMethods

Invoke-CimMethod calls a class or instance method. A method can stop a process, change a service, or otherwise modify the computer, so do not experiment with methods on an unassigned target. Prefer a purpose-built cmdlet when it provides the same operation with clearer help and safety features.

Inspect disks, memory, accounts, and adapters

Get-CimInstance -ClassName Win32_LogicalDisk -Filter 'DriveType = 3' |
    Select-Object DeviceID, VolumeName,
        @{ Name = 'SizeGB'; Expression = { [math]::Round($_.Size / 1GB, 2) } },
        @{ Name = 'FreeGB'; Expression = { [math]::Round($_.FreeSpace / 1GB, 2) } }

Get-CimInstance -ClassName Win32_PhysicalMemory |
    Select-Object BankLabel, Manufacturer, Capacity, Speed

Get-CimInstance -ClassName Win32_UserAccount -Filter 'LocalAccount = True' |
    Select-Object Name, Disabled, SID

Get-CimInstance -ClassName Win32_NetworkAdapter |
    Where-Object PhysicalAdapter |
    Select-Object Name, MACAddress, NetEnabled

Get-CimInstance -ClassName Win32_VideoController |
    Select-Object Name, DriverVersion, AdapterRAM

Get-PnpDevice -PresentOnly |
    Group-Object Class |
    Sort-Object Count -Descending |
    Select-Object Name, Count

For normal disk and network administration, prefer purpose-built cmdlets such as Get-Volume, Get-Disk, and Get-NetIPConfiguration. CIM remains valuable for consistent inventory and classes that have no simpler command.

Avoid Win32_Product for software inventory

A query against Win32_Product can be slow and can trigger Windows Installer consistency checks. Do not use it as a general software inventory mechanism. If installed-software data is required, use an approved inventory system or read the appropriate uninstall registry locations with clear 32-bit and 64-bit handling.

Build one inventory object

$inventory = [pscustomobject]@{
    ComputerName    = $computerSystem.Name
    Manufacturer    = $computerSystem.Manufacturer
    Model           = $computerSystem.Model
    OperatingSystem = $operatingSystem.Caption
    Version         = $operatingSystem.Version
    LastBoot        = $operatingSystem.LastBootUpTime
    Processor       = $processor.Name
    MemoryGB        = [math]::Round($computerSystem.TotalPhysicalMemory / 1GB, 2)
    SerialNumber    = $bios.SerialNumber
}

$inventory
$inventory | Export-Csv -Path '.\computer-inventory.csv' -NoTypeInformation

Returning a PSCustomObject makes the result easy to sort, compare, export, and test.

Practice and self-check

  1. What is the difference between a CIM class and a CIM instance?
Show solution

A class describes a type of resource and its properties and methods. An instance represents an actual resource described by that class.

  1. When is Get-ComputerInfo more convenient than several CIM queries?
Show solution

Use it for a quick, consolidated overview when its available properties meet your needs. Targeted CIM queries give more control over the data collected.

  1. Why can -Filter be more efficient than Where-Object?
Show solution

-Filter lets the CIM provider select matching instances before returning them, reducing the data transferred and processed locally. Where-Object filters objects after they have been returned.

  1. Which class reports operating-system information?
Show solution

Win32_OperatingSystem reports information such as the caption, version, architecture, and last boot time.

  1. Why should Win32_Product be avoided for routine inventory?
Show solution

Querying it can be slow and can trigger Windows Installer consistency checks. Use an approved inventory system or appropriate uninstall registry locations.

  1. Why should an inventory script return objects before formatting?
Show solution

Objects retain named properties for filtering, sorting, testing, and export. Format them only at the display stage so those properties remain usable.

Summary

Use Get-ComputerInfo for a quick overview and CIM for targeted, discoverable Windows inventory. Query only required data, filter near the provider, prefer purpose-built cmdlets where available, and combine results into structured objects.
