Hands-on — Parameters, step by step

08 - Parameters

Originele pagina openen →

Goal

Build a small script one step at a time. Then use what you learned to write another script yourself.

Learning objectives

By the end of this lab, you can:

  • Pass a value to a named parameter.
  • Add parameters and default values to a script.
  • Inspect a saved script's parameter syntax with Get-Command -Syntax.
  • Use string, integer, mandatory, and switch parameters.
  • Restrict input with ValidateRange and ValidateSet.
  • Explain [CmdletBinding()] and try -Verbose.
  • Recognise positional arguments.

Prerequisites

  • Complete the introduction and variables hands-on labs.
  • Complete the parameters lesson before starting this lab.
  • Be able to create, save, inspect, and run a .ps1 file.

Environment and safety requirements

Use PowerShell 7 and Visual Studio Code on your Windows lab computer. Your instructor must prepare C:\powershell with writable access before the lab. Routine lab commands do not need elevation once that access is ready. The scripts display messages and do not change system settings.

How to work in this lab

Use two places:

  • Editor: change the contents of your .ps1 file in Visual Studio Code.
  • Terminal: run the commands shown under Run in PowerShell.

Follow this cycle: predict → save → run → inspect → explain.

When a step says Replace the script, replace the entire file with the shown version. Each version keeps earlier features and adds the next one. Do not put the Run commands in the script file.

Keep the same terminal open. Save with Ctrl+S after each change. Work through the parts in order; the final exercise uses the features you practised.

After attempting each activity, open Show solution to check your commands, expected results, and explanations. The final exercise and self-check also have solutions. Keep the session and setup required by the activity. If you already changed a file or variable, compare its result rather than replaying the change from the solution.

Part 1 — Try a parameter you already have

Review: Parameter names and argument values.

Activity 1.1 — Change a command's input

Predict

Which output will contain only a formatted date, and which input controls it?

A parameter is a named input. An argument is the value you give it. Parameters let you change a command's behaviour without rewriting the command.

Run these commands in the terminal:

Get-Date
Get-Date -Format 'yyyy-MM-dd'

Format chooses how the date is displayed. yyyy-MM-dd means year, month, and day. The displayed date depends on when you run the command.

Check your understanding:

  1. Which part of the second command is the parameter name?
  2. Which part is the argument value?
  3. How does the second output differ from the first?

Checkpoint: Identify the parameter, its argument, and the date display difference.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Solution and explanation:

  1. Format is the parameter name, written as -Format in the call.
  2. 'yyyy-MM-dd' is its argument value.
  3. The second call displays only the date in year-month-day order. The first normally includes a time and uses the host's default display format.

The calendar date changes with the day of execution. The first display also varies with the computer's culture and current time.

Part 3 — Make the topic an input

Review: The parameter block and defaults.

Activity 3.1 — Add your first parameter

Editing the file every time you want a different topic is inconvenient. A parameter lets you supply the topic when you run the script.

Replace the script with this version and save:

param(
    [string]$Topic
)

Write-Output "Study topic: $Topic"

param() declares the script's inputs. It belongs before executable statements. [string] means the input is text. $Topic stores the supplied value inside the script.

Predict the two messages, then Run:

.\New-StudyMessage.ps1 -Topic 'PowerShell'
.\New-StudyMessage.ps1 -Topic 'Windows services'

Use quotes around a value containing spaces. Put a hyphen before the parameter name when calling the script; use $ before the variable name inside it.

Inspect the saved parameter definition without running the script body:

Get-Command .\New-StudyMessage.ps1 -Syntax

Read the syntax line using the lesson's parameter block explanation. Save and rerun this command whenever you change the script's parameters.

Check your understanding:

  1. What is the parameter called?
  2. Why are quotes useful around 'Windows services'?
  3. Did you need to edit the script between these two calls?
  4. What syntax line is shown? What do <string> and the outer brackets mean?

Checkpoint: Run both supplied topics and inspect the saved parameter syntax.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Solution and explanation:

  1. The parameter is Topic; the script uses the variable $Topic.

  2. Quotes keep Windows services together as one text argument.

  3. No edit is needed between calls. Each caller supplies the new topic.

  4. The syntax line is:

    .\New-StudyMessage.ps1 [[-Topic] <string>]

    <string> means a text value. The outer brackets make the complete input optional; the inner brackets mean the parameter name can be omitted for a positional call. A resolved-path header may also appear. This command shows syntax without producing the script's study message.

Expected output, one line per call:

Study topic: PowerShell
Study topic: Windows services

The parameter block belongs before executable statements. Comments, blank lines, directives, and script attributes may precede it.

Predict, then Run:

.\New-StudyMessage.ps1
.\New-StudyMessage.ps1 -Topic 'Networking'

Check your understanding:

  1. Which topic is used when you leave out -Topic?
  2. Does a supplied topic replace the default?

Checkpoint: Demonstrate the omitted input and a supplied replacement for the default.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Solution and explanation:

  1. The omitted input uses the default topic PowerShell.
  2. A supplied topic overrides the default, producing Study topic: Networking.

The first call produces Study topic: PowerShell. No required parameter has been introduced yet, so omitting the topic does not prompt.

Part 4 — Add a number and require a topic

Review: Typed and mandatory inputs.

Activity 4.1 — Add the number of study hours

Add a second input so you can change the study time. [int] means a whole number. Separate parameter declarations with a comma.

Replace the script with this version and save:

param(
    [string]$Topic = 'PowerShell',
    [int]$Hours = 2
)

Write-Output "Study topic: $Topic"
Write-Output "Hours: $Hours"

Predict, then Run each call separately:

.\New-StudyMessage.ps1 -Topic 'Files'
.\New-StudyMessage.ps1 -Topic 'Files' -Hours 4
.\New-StudyMessage.ps1 -Topic 'Files' -Hours 'many'

The last call intentionally uses invalid input. An error here is part of the exercise. Read which parameter it names, then continue.

Check your understanding:

  1. Which hours value is used by the first call?
  2. What changes when you supply -Hours 4?
  3. Why can 'many' not be used for this parameter?

Checkpoint: Compare default and supplied hours, then identify the deliberate conversion error.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Solution and explanation:

  1. The first call uses the default Hours = 2.
  2. The second call displays Hours: 4 instead.
  3. 'many' cannot be converted to an integer. Binding fails before the script writes a message.

First call:

Study topic: Files
Hours: 2

Second call:

Study topic: Files
Hours: 4

The third call reports an argument conversion error naming Hours. Exact error wording can vary with PowerShell version and language.

Activity 4.2 — Make the topic mandatory

Predict

What should PowerShell do when you omit the now-required topic?

Mandatory means required. Require a topic so a caller must choose one. Remove its default and add [Parameter(Mandatory)] above it.

Replace the script with this version and save:

param(
    [Parameter(Mandatory)]
    [string]$Topic,

    [int]$Hours = 2
)

Write-Output "Study topic: $Topic"
Write-Output "Hours: $Hours"

Run in the terminal:

.\New-StudyMessage.ps1 -Topic 'Files'
.\New-StudyMessage.ps1

For the second call, type Practice when PowerShell asks for Topic, then press Enter. This prompt is expected in an interactive terminal. Supply the value explicitly when a script must run unattended.

After saving this mandatory version, inspect its syntax again:

Get-Command .\New-StudyMessage.ps1 -Syntax

Check your understanding:

  1. Which line makes the topic required?
  2. What happens if you leave out the required topic in this terminal?
  3. How does the syntax now distinguish required Topic from optional Hours?

Checkpoint: Record an explicit topic and the expected interactive prompt; leave policy unchanged.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Solution and explanation:

  1. [Parameter(Mandatory)] makes Topic required.

  2. Omitting it in an interactive terminal produces a prompt. After entering Practice, the script displays that topic and the default two hours.

  3. The syntax line is:

    .\New-StudyMessage.ps1 [-Topic] <string> [[-Hours] <int>] [<CommonParameters>]

    Topic has no outer brackets around its complete input, so its value is required. Hours has outer brackets and is optional; <int> indicates a whole-number value. [<CommonParameters>] represents built-in options such as -Verbose; [Parameter(Mandatory)] also enables advanced handling.

The first call displays the Files topic with Hours: 2. The second produces:

Study topic: Practice
Hours: 2

The prompt's wording varies by host.

Part 5 — Check the input

Review: Validation rules.

Activity 5.1 — Allow only a useful number of hours

Predict

Which calls should pass the range rule, including its two boundary values?

A number such as 99 is a valid integer but not a useful study time for this script. Validation checks whether a supplied value follows a rule.

Replace the script with this version and save:

param(
    [Parameter(Mandatory)]
    [string]$Topic,

    [ValidateRange(1, 10)]
    [int]$Hours = 2
)

Write-Output "Study topic: $Topic"
Write-Output "Hours: $Hours"

ValidateRange(1, 10) allows values from 1 through 10, including both ends.

Run each call separately:

.\New-StudyMessage.ps1 -Topic 'Files' -Hours 3
.\New-StudyMessage.ps1 -Topic 'Files' -Hours 99

Now try -Hours 1 and -Hours 10 yourself.

Check your understanding:

  1. Which attribute checks the number of hours?
  2. Why is 99 rejected even though it is a number?
  3. Are 1 and 10 accepted?

Checkpoint: Verify accepted boundaries and explain why the out-of-range integer fails.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Solution and explanation:

  1. [ValidateRange(1, 10)] checks the permitted range.
  2. 99 can be converted to an integer, but it is outside that range.
  3. 1 and 10 both work because the range is inclusive.

The valid supplied call displays:

Study topic: Files
Hours: 3

The 99 call reports a validation error naming Hours and returns no study message. To test the two boundaries, run:

.\New-StudyMessage.ps1 -Topic 'Files' -Hours 1
.\New-StudyMessage.ps1 -Topic 'Files' -Hours 10

Expect Hours: 1 and Hours: 10, respectively.

Activity 5.2 — Offer a small list of choices

Predict

Which priorities should be accepted, and what happens when one is omitted?

Add a priority. ValidateSet limits input to a listed set of values.

Replace the script with this version and save:

param(
    [Parameter(Mandatory)]

    [ValidateRange(1, 10)]

Write-Output "Study topic: $Topic"

.\New-StudyMessage.ps1 -Topic 'Files' -Priority Urgent

Check your understanding:

  1. What is the default priority?
  2. Which three priority values are allowed?
  3. Why is Urgent rejected?

Show solution

Solution and explanation:

  1. The default priority is Medium.
  2. Allowed values are Low, Medium, and High.
  3. Urgent is outside the set, so parameter validation rejects it.

Hours: 2

Part 6 — Turn an option on or off

Review: Switch values.

Activity 6.1 — Add a switch

A switch is an on/off option. Add -Detailed to request an extra message. A switch does not need a separate value after its name.

Replace the script with this version and save:

param(
    [Parameter(Mandatory)]
    [string]$Topic,

    [ValidateRange(1, 10)]
    [int]$Hours = 2,

    [ValidateSet('Low', 'Medium', 'High')]
    [string]$Priority = 'Medium',

    [switch]$Detailed
)

Write-Output "Study topic: $Topic"
Write-Output "Hours: $Hours"
Write-Output "Priority: $Priority"

if ($Detailed) {
    Write-Output "Plan: Study $Topic for $Hours hour(s)."
}

if ($Detailed) runs the statements inside its braces only when the switch is true. You will practise if in more detail in the next lab.

Predict which calls show the extra plan, then Run:

.\New-StudyMessage.ps1 -Topic 'Files'
.\New-StudyMessage.ps1 -Topic 'Files' -Detailed
.\New-StudyMessage.ps1 -Topic 'Files' -Detailed:$false

The colon in -Detailed:$false explicitly turns the option off. A supplied switch can therefore be false. Test its value when deciding what to do.

Check your understanding:

  1. Which call enables the extra message?
  2. Does leaving out -Detailed enable it?
  3. Does -Detailed:$false enable it?

Checkpoint: Compare absent, enabled, and explicitly false switch values.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Solution and explanation:

  1. The second call, with -Detailed, enables the extra plan.
  2. Leaving out the switch leaves it false, so no plan is displayed.
  3. -Detailed:$false supplies a false switch value, so no plan is displayed.

All three calls display the topic, hours, and priority. Only the second also adds:

Plan: Study Files for 2 hour(s).

The condition tests the switch's value. Being supplied is different from being true.

Part 7 — Add optional diagnostic output

Review: Cmdlet binding and verbose output.

Activity 7.1 — Use [CmdletBinding()] and -Verbose

A diagnostic message explains what a script is doing. Write-Verbose lets a caller request that message without changing the normal output.

[CmdletBinding()] explicitly marks the script for cmdlet-style handling. It provides common parameters such as -Verbose. Place it before param(). The earlier [Parameter()] attribute also enables advanced handling; using [CmdletBinding()] makes that intention clear at the top of the script.

Replace the script with this version and save:

[CmdletBinding()]
param(
    [Parameter(Mandatory)]
    [string]$Topic,

    [ValidateRange(1, 10)]
    [int]$Hours = 2,

    [ValidateSet('Low', 'Medium', 'High')]
    [string]$Priority = 'Medium',

    [switch]$Detailed
)

Write-Verbose 'Preparing the study message'

Write-Output "Study topic: $Topic"
Write-Output "Hours: $Hours"
Write-Output "Priority: $Priority"

if ($Detailed) {
    Write-Output "Plan: Study $Topic for $Hours hour(s)."
}

Predict the difference, then Run:

.\New-StudyMessage.ps1 -Topic 'Files'
.\New-StudyMessage.ps1 -Topic 'Files' -Verbose

You do not need to declare a custom Verbose parameter.

Check your understanding:

  1. Where is [CmdletBinding()] placed?
  2. Which call displays the diagnostic message?
  3. Does -Verbose change the topic or number of hours?

Checkpoint: Keep normal output separate from the requested diagnostic message.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Solution and explanation:

  1. [CmdletBinding()] is immediately before param(), outside its parentheses.
  2. The call with -Verbose displays Preparing the study message as a diagnostic message. Both calls retain the same normal output.
  3. -Verbose does not change the topic or hours.

Verbose output is normally hidden. If a student has changed the session's $VerbosePreference, both calls may show the message; use a fresh default session when demonstrating the difference. [Parameter()] already enables advanced handling, so the added attribute makes it explicit rather than introducing a previously unavailable custom Verbose input.

Part 8 — Recognise positional arguments

Review: Explicit positions.

Activity 8.1 — Try a shorter call

A positional argument leaves out the parameter name. Its position decides which input receives the value. Prefer names when they make a call clearer.

Replace the script with this version and save:

[CmdletBinding()]
param(
    [Parameter(Mandatory, Position = 0)]
    [string]$Topic,

    [Parameter(Position = 1)]
    [ValidateRange(1, 10)]
    [int]$Hours = 2,

    [ValidateSet('Low', 'Medium', 'High')]
    [string]$Priority = 'Medium',

    [switch]$Detailed
)

Write-Verbose 'Preparing the study message'

Write-Output "Study topic: $Topic"
Write-Output "Hours: $Hours"
Write-Output "Priority: $Priority"

if ($Detailed) {
    Write-Output "Plan: Study $Topic for $Hours hour(s)."
}

The new Position values explicitly define Topic as position 0 and Hours as position 1. Positions count from zero.

Predict, then Run:

.\New-StudyMessage.ps1 -Topic 'Files' -Hours 3
.\New-StudyMessage.ps1 'Files' 3

Check your understanding:

  1. Which parameter receives 'Files' in the shorter call?
  2. Which parameter receives 3?
  3. Which call is easier for a new reader to understand, and why?

Checkpoint: Show equivalent named and positional calls and identify both input positions.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Solution and explanation:

  1. Files binds to Topic at position 0.
  2. 3 binds to Hours at position 1.
  3. Prefer the named call for a new reader because it states each input's purpose. A justified preference for short interactive calls is acceptable.

Both calls display:

Study topic: Files
Hours: 3
Priority: Medium

The final guided version is also included in New-StudyMessage.ps1.

Part 9 — Final exercise: a report request

Filename: New-ReportRequest.ps1

Activity 9.1 — Build your own script

Predict

Which test calls should display a request, and which should fail before output?

You have built one script with guidance. Now create a different script using the same techniques. A report request describes what a report should contain. Your script only displays that request; it does not create a report file.

Step 1 — Create the file

In your lab folder, create and save New-ReportRequest.ps1:

code .\New-ReportRequest.ps1

You can also create the file manually in Visual Studio Code.

Step 2 — Add the inputs

Put [CmdletBinding()] before param(). Use this checklist:

Parameter Type Rule
Name [string] Mandatory; no default.
Top [int] Default 5; allow 1 through 20.
Format [string] Default Table; allow Table, Csv, Json.
IncludeDetails [switch] Request an extra message when true.

Use the guided script to remember how each feature is written. Choose named arguments for the test calls; you do not need to define explicit positions.

Step 3 — Display the request

Use Write-Output to display the report name, Top, and Format. Add an if block that displays an extra message only when IncludeDetails is true. Save your script.

Step 4 — Test it

Predict the result first. Then run each call separately:

.\New-ReportRequest.ps1 -Name Inventory
.\New-ReportRequest.ps1 -Name Services -Top 10 -Format Json -IncludeDetails
.\New-ReportRequest.ps1 -Name Inventory -Top 50
.\New-ReportRequest.ps1 -Name Inventory -Format Xml
.\New-ReportRequest.ps1 -Name Inventory -IncludeDetails:$false

Check your understanding:

  1. Which default values are used by the first call?
  2. What changes in the second call?
  3. Why is the third call rejected?
  4. Why is the fourth call rejected?
  5. Should the fifth call display the extra message? Explain.

Checkpoint: Save your own script and record predictions, output, and explanations for all five calls.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Save this implementation as New-ReportRequest.ps1 in your parameters lab folder before running the five test calls above.

Report-request solution:

[CmdletBinding()]
param(
    [Parameter(Mandatory)]
    [string]$Name,

    [ValidateRange(1, 20)]
    [int]$Top = 5,

    [ValidateSet('Table', 'Csv', 'Json')]
    [string]$Format = 'Table',

    [switch]$IncludeDetails
)

Write-Output "Report name: $Name"
Write-Output "Top: $Top"
Write-Output "Format: $Format"

if ($IncludeDetails) {
    Write-Output 'Extra details requested.'
}
  1. The first call uses Top = 5 and Format = Table; the switch defaults to false, so there is no extra message.
  2. The second call selects Services, Top = 10, and Format = Json, and enables the extra-details message.
  3. 50 is outside the permitted inclusive range 1 through 20.
  4. Xml is not in the allowed set Table, Csv, Json.
  5. The fifth call should not display the extra message because the switch's value is explicitly false.

The first call displays Report name: Inventory, Top: 5, and Format: Table. The second displays Report name: Services, Top: 10, Format: Json, and Extra details requested. Calls three and four report validation errors without producing request text; the fifth produces the same three normal lines as the first.

Show solution Optimized

The same validation and switch behavior can be kept while grouping the output lines. Save this alternative as New-ReportRequest.ps1.

[CmdletBinding()]
param(
    [Parameter(Mandatory)]
    [string]$Name,

    [ValidateRange(1, 20)]
    [int]$Top = 5,

    [ValidateSet('Table', 'Csv', 'Json')]
    [string]$Format = 'Table',

    [switch]$IncludeDetails
)

@(
    "Report name: $Name"
    "Top: $Top"
    "Format: $Format"
    if ($IncludeDetails) {
        'Extra details requested.'
    }
) | Write-Output

Summary

Start with a small script and add one feature at a time. Parameters let the caller supply input. Defaults provide optional values, mandatory parameters require input, validation checks values, and switches control options. [CmdletBinding()] makes cmdlet-style handling explicit, including common parameters such as -Verbose.
