Hands-on — Regular expressions

05 - Regular expressions

Originele pagina openen →

Goal

Use regular expressions to recognise, extract, search, replace, and split predictable text without changing any important data.

Learning objectives

By the end of this lab, you can:

  • distinguish literal text, wildcard patterns, and regular expressions;
  • choose a suitable matching approach for a practical administration task;
  • use anchors, character classes, metacharacters, and quantifiers;
  • test text with -match and -cmatch;
  • extract values with numbered and named capture groups;
  • find one or more matches with Select-String;
  • replace or split text using a regex pattern; and
  • parse structured log lines into PowerShell objects.

Prerequisites

  • Complete Regular expressions before starting this lab.

Why use regex in this lab?

In daily administration, wildcards help select names: *.log selects log files, and PC-* selects computer names starting with PC-. With -like, * means zero or more characters, and the pattern must match the whole string.

Regex describes text in more detail. You can require a fixed number of digits, extract a domain and user into separate values, or mask part of an identifier. In this lab, you will compare filename selection with filename validation, extract values, and search log contents. These steps help turn text into data that a script can use for reports and decisions.

Use -eq for one exact value, -like for a wildcard pattern, and -match for regex. Select-String -Pattern also uses regex. The pattern language is chosen by the operator or parameter; a pattern cannot be copied between them without checking its meaning.

How to work in this lab

For every activity, complete the three steps.

  1. Predict: write or discuss what you think will happen.
  2. Run: enter the command exactly as shown.
  3. Reflect: explain the result in your own words.

Regex patterns can match more or less text than intended. Always test representative valid, invalid, and boundary cases before using a pattern in automation.

After attempting each activity, open Show solution to check your commands, expected results, and explanations. The final exercise and self-check also have solutions. Keep the session and setup required by the activity. If you already changed a file or variable, compare its result rather than replaying the change from the solution.

Activity 1.4 — Choose a pattern for support report filenames

A support folder contains dated reports, notes, and backups. One task selects all report log files. Another accepts only filenames shaped like report-YYYY-MM-DD.log.

For this activity, -like uses * for any sequence of characters. In regex, [0-9]{4} requires four ASCII digits, \. matches a literal dot, and ^ and $ mark the start and end. Part 2 explores these building blocks further.

Predict

Which filenames will each filter return? Will the two filters return the same names?

Run

Create the sample names and run the wildcard filter. This creates no files.

$reportNames = @(
    'report-2026-10-16.log'
    'report-notes.log'
    'report-2026-1.log'
    'old-report-2026-10-16.log'
    'report-2026-10-16.log.bak'
)

$reportNames | Where-Object { $_ -like 'report-*.log' }

Keep the same session open and run the regex filter on $reportNames.

$reportNames | Where-Object {
    $_ -match '^report-[0-9]{4}-[0-9]{2}-[0-9]{2}\.log$'
}

Reflect

  1. Which names does each filter return? Compare with your prediction.
  2. Why can the wildcard accept a report name that does not contain a date?
  3. What roles do [0-9]{4}, [0-9]{2}, \., ^, and $ play here?
  4. Which approach fits selecting all report log files? Which fits checking the required filename structure? Explain your choices.
  5. Could report-2026-99-99.log pass the regex? Would that prove its date exists? Explain the difference between checking shape and a calendar date.
  6. Could a wildcard use repeated [0-9] ranges for this format too? Why might regex become convenient as a pattern grows or needs captured values?

Checkpoint: Record both sets of filenames and justify a pattern choice for each support task.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected filter results:

The wildcard returns report-2026-10-16.log, report-notes.log, and report-2026-1.log. The regex returns only report-2026-10-16.log.

Prediction and reflection answers:

  1. Which names does each filter return? Compare with your prediction. The wildcard returns the three names shown above; the regex returns only report-2026-10-16.log. Both reject the extra prefix and backup suffix.
  2. Why can the wildcard accept a report name that does not contain a date? Its * accepts any sequence, including notes or 2026-1. It places no digit or date-format requirements on that part of the name.
  3. What roles do [0-9]{4}, [0-9]{2}, \., ^, and $ play here? The first two require four and two ASCII digits. \. requires a literal dot. The anchors require the name to start with report- and end after .log, rejecting additional text.
  4. Which approach fits selecting all report log files? Which fits checking the required filename structure? Explain your choices. The wildcard is concise for selecting the report logs regardless of their middle portion. The regex explicitly checks the required digit counts and separators.
  5. Could report-2026-99-99.log pass the regex? Would that prove its date exists? Explain the difference between checking shape and a calendar date. Yes, it matches the shape, but month 99 and day 99 do not exist. Use date parsing as well when the date must be valid.
  6. Could a wildcard use repeated [0-9] ranges for this format too? Why might regex become convenient as a pattern grows or needs captured values? Yes. For example, the four-digit year could use [0-9][0-9][0-9][0-9] with -like. Regex expresses repetition compactly with {4} and can capture parts for later commands; wildcards do not populate $Matches with captured values.

Activity 3.3 — Use named capture groups

Named capture groups let you extract values by a meaningful name. Compare matching the same text without capture groups and with named capture groups.

Checkpoint: Record both results and explain how capture groups change the values you can extract from a successful match.

Prediction and reflection answers:

Part 6 — Challenge: parse structured log lines

Filename: Convert-LogLines.ps1

Save the supplied data and your challenge commands in this file. Run . .\Convert-LogLines.ps1 in your lab session.

Scenario

An operations team receives log lines in this format:

LEVEL|CODE|MESSAGE

Valid levels are INFO, WARN, and ERROR. A valid code contains exactly three uppercase letters followed by exactly three digits.

Your task

Use this data:

$logLines = @(
    'INFO|NET100|Connection established'
    'ERROR|NET503|Gateway unavailable'
    'WARN|SEC210|Password expires soon'
    'DEBUG|APP200|Debug details'
    'ERROR|BAD5|Invalid code format'
)
  1. Write one anchored regex with named groups Level, Code, and Message.
  2. Parse only valid lines into objects with those three properties.
  3. Store the objects in $parsedLogs.
  4. Display the objects sorted by Level and Code.
  5. Group the parsed objects by Level and display Name and Count.
  6. Explain why the DEBUG and BAD5 lines are rejected.

Suggested starting point

$pattern = '...'

$parsedLogs = $logLines | ForEach-Object {
    if ($_ -cmatch $pattern) {
        [pscustomobject]@{
            Level   = $Matches.Level
            Code    = $Matches.Code
            Message = $Matches.Message
        }
    }
}

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Use the log lines supplied in the challenge. The solution creates $parsedLogs from those strings; it does not change the practice log files.

Log-parsing solution (Beginner):

$logLines = @(
    'INFO|NET100|Connection established'
    'ERROR|NET503|Gateway unavailable'
    'WARN|SEC210|Password expires soon'
    'DEBUG|APP200|Debug details'
    'ERROR|BAD5|Invalid code format'
)

$pattern = '^(?<Level>INFO|WARN|ERROR)\|(?<Code>[A-Z]{3}\d{3})\|(?<Message>.+)$'

$parsedLogs = $logLines | ForEach-Object {
    if ($_ -cmatch $pattern) {
        [pscustomobject]@{
            Level   = $Matches.Level
            Code    = $Matches.Code
            Message = $Matches.Message
        }
    }
}

$parsedLogs | Sort-Object Level, Code
$parsedLogs | Group-Object Level | Sort-Object Name | Select-Object Name, Count

Three objects are produced: INFO/NET100, ERROR/NET503, and WARN/SEC210. The grouped result contains one object for each level. DEBUG is rejected because the Level group permits only INFO, WARN, or ERROR; BAD5 is rejected because a code must contain three uppercase letters followed by three digits. -cmatch enforces uppercase letters, and the anchors require the entire line to follow the format.

Show solution Optimized

Use the log lines supplied in the challenge.

Log-parsing solution (Optimized):

$logLines = @(
    'INFO|NET100|Connection established'
    'ERROR|NET503|Gateway unavailable'
    'WARN|SEC210|Password expires soon'
    'DEBUG|APP200|Debug details'
    'ERROR|BAD5|Invalid code format'
)

$pattern = '^(?<Level>INFO|WARN|ERROR)\|(?<Code>[A-Z]{3}\d{3})\|(?<Message>.+)$'

$parsedLogs = @($logLines | Where-Object { $_ -cmatch $pattern } | ForEach-Object {
    [pscustomobject][ordered]@{
        Level   = $Matches.Level
        Code    = $Matches.Code
        Message = $Matches.Message
    }
})

$parsedLogs | Sort-Object Level, Code
$parsedLogs | Group-Object Level | Select-Object -ExpandProperty Name, Count

The optimized version combines filtering and object creation in one pipeline, uses [ordered] to preserve property order in the output, and simplifies the grouping display. Both versions validate the same rules and produce three valid log entries with grouped counts by level.

Summary

Use wildcards for simple name selection and regex for structural checks, extraction, and selective replacement. Anchors control position, character classes define allowed characters, quantifiers define repetition, and groups extract useful parts. PowerShell integrates regex through -match, -replace, -split, and Select-String. Test patterns against representative non-matches as carefully as successful matches.
