Hands-on — Windows information

15 - Windows information

Originele pagina openen →

Goal

Collect a focused Windows hardware and operating-system inventory as reusable PowerShell objects.

Learning objectives

By the end of this lab, you can:

  • compare Get-ComputerInfo with targeted CIM queries;
  • discover CIM classes and inspect their members;
  • filter processes and fixed disks efficiently;
  • calculate readable inventory values; and
  • create and verify a reusable inventory script and CSV report.

Prerequisites

  • Complete 14 — Local user accounts.
  • Complete Collecting Windows information before starting this lab.
  • Use PowerShell on Windows.

How to work in this lab

All activities are read-only except writing files to your dedicated lab folder. Keep data structured until the final display or export.

Part 1 — Prepare the workspace

Activity 1.1 — Create the lab folder

$labRoot = Join-Path 'C:\powershell' 'Windows-Information-Lab'
New-Item -Path $labRoot -ItemType Directory -Force
Set-Location -Path $labRoot

Activity 2.2 — Discover CIM classes

Get-CimClass -ClassName 'Win32_*OperatingSystem*' |
    Select-Object CimClassName

Get-CimClass -ClassName Win32_OperatingSystem |
    Select-Object -ExpandProperty CimClassProperties |
    Select-Object -First 15 Name, CimType

Reflect

What is the difference between a class definition and an instance?

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results and reflection answer: The first query lists matching CIM class names; the second displays up to 15 property names and CIM types. A class defines a resource type, while an instance represents an actual resource of that type.

Part 3 — Query focused system information

Activity 3.1 — Operating system and computer system

$os = Get-CimInstance -ClassName Win32_OperatingSystem
$computer = Get-CimInstance -ClassName Win32_ComputerSystem

$os | Select-Object CSName, Caption, Version, OSArchitecture, LastBootUpTime
$computer | Select-Object Name, Manufacturer, Model, TotalPhysicalMemory

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results: The two queries return operating-system and computer-system properties, including the OS caption and physical memory. Values such as model and boot time vary by computer and execution.

Activity 3.2 — Processor, BIOS, and baseboard

$processor = Get-CimInstance -ClassName Win32_Processor | Select-Object -First 1
$bios = Get-CimInstance -ClassName Win32_BIOS
$baseboard = Get-CimInstance -ClassName Win32_BaseBoard | Select-Object -First 1

$processor | Select-Object Name, NumberOfCores, NumberOfLogicalProcessors
$bios | Select-Object Manufacturer, SMBIOSBIOSVersion, SerialNumber
$baseboard | Select-Object Manufacturer, Product, SerialNumber

Reflect

Why does the example select only the first processor and baseboard instance?

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results and reflection answer: The selected properties describe the first processor and baseboard, plus the BIOS. Selecting one instance keeps this simple report to one value per component; it can omit additional processors or boards. Values vary by computer.

Activity 3.3 — Fixed disks

$fixedDisks = Get-CimInstance -ClassName Win32_LogicalDisk -Filter 'DriveType = 3' |
    Select-Object DeviceID, VolumeName,
        @{ Name = 'SizeGB'; Expression = { [math]::Round($_.Size / 1GB, 2) } },
        @{ Name = 'FreeGB'; Expression = { [math]::Round($_.FreeSpace / 1GB, 2) } }

$fixedDisks

Reflect

  1. Where is the disk filter executed?
  2. Why are bytes converted to gigabytes?

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results and reflection answers: The CIM provider applies DriveType = 3 before returning fixed logical disks. The calculated SizeGB and FreeGB properties make byte quantities easier to read; the values and number of disks vary by computer.

Activity 3.4 — Processes and adapters

Get-CimInstance -ClassName Win32_Process -Filter "Name LIKE 'P%'" |
    Select-Object Name, ProcessId, WorkingSetSize

Get-CimInstance -ClassName Win32_NetworkAdapter |
    Where-Object PhysicalAdapter |
    Select-Object Name, MACAddress, NetEnabled

Reflect

Why is Win32_Product not used for software inventory?

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results and reflection answer: The first query selects processes with names beginning with P; the second selects physical adapters. Results vary and may be empty. Win32_Product can be slow and trigger Windows Installer consistency checks, so it is unsuitable for routine inventory.

Part 4 — Challenge: build an inventory script

Filename: Get-WindowsInventory.ps1

Create Get-WindowsInventory.ps1. It must:

  • use [CmdletBinding()];
  • accept optional OutputPath;
  • query Win32_OperatingSystem, Win32_ComputerSystem, Win32_Processor, and Win32_BIOS;
  • return one PSCustomObject with computer name, manufacturer, model, OS, version, architecture, last boot, processor, memory in GB, serial number, and fixed-disk count;
  • round memory to two decimal places;
  • export the object when OutputPath is supplied; and
  • still write the object to the success-output stream.

Test:

.\Get-WindowsInventory.ps1

$csvPath = Join-Path $labRoot 'computer-inventory.csv'
.\Get-WindowsInventory.ps1 -OutputPath $csvPath
Import-Csv -Path $csvPath

Reflect

  2. Which imported CSV properties become strings?
  3. How would you extend the script for several authorized computers?

Student requirements: Build Get-WindowsInventory.ps1 with the four required CIM classes, one report object, rounded memory, fixed-disk count, optional CSV export, and continued object output.

Detailed solution: Use Get-WindowsInventory.ps1. It queries each class once, builds the object before exporting, validates the output directory, and returns the same object to the caller.

.\Get-WindowsInventory.ps1
$csvPath = Join-Path $labRoot 'computer-inventory.csv'
.\Get-WindowsInventory.ps1 -OutputPath $csvPath
Import-Csv -Path $csvPath

Questions and detailed answers

  1. Object output allows assignment, further pipelines, tests, and formats other than CSV.
  2. CSV imports fields as strings, including memory, disk count, and the last-boot value.
  3. Add a validated computer-name parameter or CIM-session input, query each authorized target, catch per-target failures, and add a computer-name/error result for every request.
Show solution Optimized

The existing script above is the step-by-step version. This alternative keeps the same properties and uses a provider-side filter for the disk count. Save it as Get-WindowsInventory.ps1.

[CmdletBinding()]
param([string]$OutputPath)

if (-not $IsWindows) { throw 'This script requires Windows.' }

$os = Get-CimInstance Win32_OperatingSystem -ErrorAction Stop
$computer = Get-CimInstance Win32_ComputerSystem -ErrorAction Stop
$processor = Get-CimInstance Win32_Processor -ErrorAction Stop | Select-Object -First 1
$bios = Get-CimInstance Win32_BIOS -ErrorAction Stop
$disks = @(Get-CimInstance Win32_LogicalDisk -Filter 'DriveType = 3' -ErrorAction Stop)

$result = [pscustomobject]@{
    ComputerName    = $computer.Name
    Manufacturer    = $computer.Manufacturer
    Model           = $computer.Model
    OperatingSystem = $os.Caption
    Version         = $os.Version
    Architecture    = $os.OSArchitecture
    LastBoot        = $os.LastBootUpTime
    Processor       = $processor.Name
    MemoryGB        = [math]::Round($computer.TotalPhysicalMemory / 1GB, 2)
    SerialNumber    = $bios.SerialNumber
    FixedDiskCount  = $disks.Count
}

if ($OutputPath) {
    $parent = Split-Path -Path $OutputPath -Parent
    if ($parent -and -not (Test-Path -LiteralPath $parent -PathType Container)) {
        throw "Output directory does not exist: $parent"
    }
    $result | Export-Csv -Path $OutputPath -NoTypeInformation -ErrorAction Stop
}
$result

Inventory values differ between computers and runs.
