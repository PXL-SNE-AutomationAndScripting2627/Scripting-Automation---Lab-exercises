Hands-on — Exception handling

11 - Exception handling

Originele pagina openen →

Goal

Handle expected failures without hiding useful diagnostics or leaving a script in an unclear state.

Learning objectives

By the end of this lab, you can:

  • distinguish terminating and non-terminating errors;
  • make a cmdlet error catchable with -ErrorAction Stop;
  • use try, catch, and finally;
  • inspect the current error record and exception;
  • throw a clear exception for invalid state; and
  • return consistent success and failure result objects.

Prerequisites

  • Complete Exception handling before starting this lab.
  • Complete 10 — Loops.
  • Understand conditions, parameters, and object output.

How to work in this lab

The lab deliberately causes controlled errors. Run one activity at a time and read every error message.

After attempting each activity, open Show solution to check your commands, expected results, and explanations. The final exercise and self-check also have solutions. Keep the session and setup required by the activity. If you already changed a file or variable, compare its result rather than replaying the change from the solution.

Part 2 — Catch errors

Activity 2.1 — Compare Continue and Stop

try {
    Get-Item -Path $missingPath -ErrorAction Continue
    'Try block continued after Continue.'
} catch {
    'Catch block ran.'
}

Then:

try {
    Get-Item -Path $missingPath -ErrorAction Stop
    'This line should not run.'
} catch {
    'Catch block handled the missing path.'
}

Reflect

  1. Which version enters catch?
  2. Why does -ErrorAction Stop matter for many cmdlets?

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results and reflection answers:

Continue does not enter catch; Stop converts the cmdlet's non-terminating error into a terminating one that catch handles.

Activity 2.2 — Inspect $_ in a catch block

try {
    Get-Item -Path $missingPath -ErrorAction Stop
} catch {
    [pscustomobject]@{
        Message       = $_.Exception.Message
        ExceptionType = $_.Exception.GetType().FullName
        Category      = $_.CategoryInfo.Category
        Target        = $_.TargetObject
    }
}

Reflect

  1. What does $_ represent inside catch?
  2. Which properties would help a support technician?

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results and reflection answers:

Inside catch, $_ is the current ErrorRecord. Message, exception type, category, target, position, and invocation information can assist diagnosis.

Activity 2.3 — Use finally

$cleanupRan = $false

try {
    Get-Item -Path $missingPath -ErrorAction Stop
} catch {
    'The error was handled.'
} finally {
    $cleanupRan = $true
    'Finally ran.'
}

$cleanupRan

Reflect

  3. Name one suitable cleanup task.

Expected results and reflection answers:

Part 3 — Throw and catch specific failures

Activity 3.1 — Throw an exception deliberately

An installation needs at least 10 GB of free space. Use a simulated value to practise rejecting an unsuitable state without changing your computer. Review when to use throw. Run this example in the terminal with default error preferences. It does not depend on earlier activity variables.

Predict: Will the success message run when only 4 GB is available?

Run:

$freeSpaceGB = 4

try {
    if ($freeSpaceGB -lt 10) {
        throw "Insufficient free space: $freeSpaceGB GB."
    }

    'Enough space is available.'
} catch {
    "Validation failed: $($_.Exception.Message)"
}

'Space check finished.'

Change $freeSpaceGB = 4 to $freeSpaceGB = 20 and rerun the whole block.

Reflect

  1. Why is throw useful here?
  2. Does the success line run?
  3. What changes when you use 20 GB instead of 4 GB?
  4. Why does throw work with catch without -ErrorAction Stop?

Checkpoint: Compare both runs. Confirm that the success message is skipped for 4 GB, shown for 20 GB, and followed by Space check finished. in both cases.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results and reflection answers:

The prediction is that the success message is skipped for 4 GB.

  1. throw signals that the installation cannot proceed with the available space. No cmdlet needs to fail for your script to detect this problem.
  2. With 4 GB, execution jumps to catch, skipping the success message.
  3. With 20 GB, the condition is false, so throw is not reached. The success message runs and catch is skipped.
  4. throw already creates a terminating error. -ErrorAction Stop is used to make a cmdlet's non-terminating error catchable.

Expected output with 4 GB:

Validation failed: Insufficient free space: 4 GB.
Space check finished.

Expected output with 20 GB:

Enough space is available.
Space check finished.

The final statement runs in both cases because the failed check is handled by catch. This activity changes only the simulated session variable.

Part 5 — Challenge: produce consistent calculation results

Filename: Get-CalculationResults.ps1

Save the supplied data and your challenge commands in this file. Run . .\Get-CalculationResults.ps1 in your lab session.

Use:

$calculations = @(
    [pscustomobject]@{ Dividend = 10; Divisor = 2 }
    [pscustomobject]@{ Dividend = 9;  Divisor = 0 }
    [pscustomobject]@{ Dividend = 8;  Divisor = 4 }
)

Process every item with foreach, try, catch, and finally:

  • if the divisor is zero, throw a System.DivideByZeroException;
  • successful result objects contain Dividend, Divisor, Success = $true, Result, and a null Error;
  • failure objects contain the same properties, with Success = $false, a null Result, and the exception message;
  • increment $attemptCount in finally; and
  • display all result objects and the final attempt count.

Explain why returning the same property structure for success and failure is useful.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Use the challenge's supplied input objects in the same session.

Calculation-results solution (Beginner):

$calculations = @(
    [pscustomobject]@{ Dividend = 10; Divisor = 2 }
    [pscustomobject]@{ Dividend = 9;  Divisor = 0 }
    [pscustomobject]@{ Dividend = 8;  Divisor = 4 }
)

$attemptCount = 0
$calculationResults = @()

foreach ($calculation in $calculations) {

    try {
        if ($calculation.Divisor -eq 0) {
            throw [System.DivideByZeroException]::new("Cannot divide by zero")
        }

        $result = $calculation.Dividend / $calculation.Divisor

        $calculationResults += [pscustomobject]@{
            Dividend = $calculation.Dividend
            Divisor  = $calculation.Divisor
            Success  = $true
            Result   = $result
            Error    = $null
        }
    }
    catch {
        $calculationResults += [pscustomobject]@{
            Dividend = $calculation.Dividend
            Divisor  = $calculation.Divisor
            Success  = $false
            Result   = $null
            Error    = $_.Exception.Message
        }
    }
    finally {
        $attemptCount++
    }
}

$calculationResults | Format-Table -AutoSize
Write-Host "Total attempts: $attemptCount"

Results are 5, failure, and 2; attempt count is 3. A consistent schema lets later commands filter by Success, select common properties, and export one table without special cases.

Show solution Optimized

Use the challenge's supplied input objects in the same session.

Calculation-results solution (Optimized):


$calculations = @(
    [pscustomobject]@{ Dividend = 10; Divisor = 2 }
    [pscustomobject]@{ Dividend = 9;  Divisor = 0 }
    [pscustomobject]@{ Dividend = 8;  Divisor = 4 }
)

$calculationResults = @()
$attemptCount = 0

foreach ($calculation in $calculations) {
    try {
        $result = $null
        $errorMessage = $null
        $success = $false

        if ($calculation.Divisor -eq 0) {
            throw [System.DivideByZeroException]::new('Divisor cannot be zero.')
        }

        $result = $calculation.Dividend / $calculation.Divisor
        $success = $true
    }
    catch [System.DivideByZeroException] {
        $errorMessage = $_.Exception.Message
    }
    finally {
        $attemptCount++

        $calculationResults += [pscustomobject]@{
            Dividend = $calculation.Dividend
            Divisor  = $calculation.Divisor
            Success  = $success
            Result   = $result
            Error    = $errorMessage
        }
    }
}

$calculationResults
$attemptCount

The optimized version separates the result object creation into the finally block, ensuring consistent property initialization regardless of the code path. This reduces code duplication while maintaining the same reliable output structure. Both versions produce identical results.

Question Answer

$_ in catch Current ErrorRecord.
finally Runs whether try succeeds or fails.
throw Creates/signals a terminating error.

Summary

Good exception handling converts expected failures into explicit, useful outcomes. Catch only errors you can handle, preserve diagnostic information, and use finally for work that must always occur.
