Automating local user accounts

01 - Local user accounts

Originele pagina openen →

Local accounts are stored on one Windows computer. They are useful for standalone systems, recovery scenarios, and tightly scoped service or lab accounts. They are different from domain accounts, which are managed centrally in Active Directory.

Learning objectives

By the end of this lesson, you can:

  • inspect local users, groups, and group membership;
  • create a local user with a securely entered password;
  • add and remove local group membership;
  • reset, disable, enable, and remove a local account; and
  • apply safe automation practices to account-lifecycle changes.

Prerequisites

  • Complete the PowerShell Basics course, including functions and modules.
  • Use 64-bit PowerShell on Windows; Microsoft.PowerShell.LocalAccounts is Windows-only and is unavailable in 32-bit PowerShell on a 64-bit system.
  • Perform changes only in an instructor-provided disposable Windows VM or Windows Sandbox.
  • Start the terminal as an administrator for commands that change accounts or group membership.

Discover the local-account commands

The Microsoft.PowerShell.LocalAccounts module uses predictable Verb-Noun names.

Get-Command -Module Microsoft.PowerShell.LocalAccounts |
    Sort-Object Noun, Verb |
    Select-Object Name, CommandType

Get-Help Get-LocalUser -Examples
Get-Help New-LocalUser -Full

Common commands include:

Task Cmdlet
List or find users Get-LocalUser
Create a user New-LocalUser
Change user properties or password Set-LocalUser
Disable or enable a user Disable-LocalUser, Enable-LocalUser
Remove a user Remove-LocalUser
Inspect local groups Get-LocalGroup, Get-LocalGroupMember
Change membership Add-LocalGroupMember, Remove-LocalGroupMember

Inspect users and groups

Start with read-only discovery. Keep the objects structured until the end of the pipeline.

Get-LocalUser |
    Select-Object Name, Enabled, LastLogon, Description

Get-LocalUser -Name 'Student' |
    Select-Object *

Get-LocalGroup |
    Select-Object Name, SID, Description

Built-in group names are translated on localized Windows installations. A security identifier (SID) is stable across languages. The built-in Users group has SID S-1-5-32-545.

$usersGroup = Get-LocalGroup -SID 'S-1-5-32-545'
Get-LocalGroupMember -Group $usersGroup |
    Select-Object Name, ObjectClass, PrincipalSource

Create a local user safely

Lab account lifecycle

flowchart LR
    A["Check that the lab account is absent"] --> B["Preview and create it disabled"]
    B --> C["Add least-privilege membership"]
    C --> D["Enable when needed"]
    D --> E["Disable after use"]
    E --> F["Preview and remove the lab account"]

Perform changes only in the assigned disposable environment. Verify each state and do not reuse or remove an account you did not create.

Do not put a real password in a script, command history, screenshot, or source repository. Ask for it interactively as a SecureString.

$password = Read-Host -Prompt 'Enter the temporary password' -AsSecureString

$newUserParameters = @{
    Name        = 'PSLabStudent'
    Password    = $password
    FullName    = 'PowerShell Lab Student'
    Description = 'Disposable account for the PowerShell automation lab'
    Disabled    = $true
}

New-LocalUser @newUserParameters -WhatIf

-WhatIf previews the supported operation. After reviewing the name and description, remove -WhatIf only in the assigned lab VM.

Creating the account disabled gives the administrator time to verify properties and group membership before allowing sign-in.

Manage group membership

Use the least-privilege group required for the account's work. Do not add an account to Administrators merely to make a task easier.

$account = Get-LocalUser -Name 'PSLabStudent'
$usersGroup = Get-LocalGroup -SID 'S-1-5-32-545'

Add-LocalGroupMember -Group $usersGroup -Member $account -WhatIf
Get-LocalGroupMember -Group $usersGroup |
    Where-Object Name -Like '*\PSLabStudent'

Pass objects where possible. This avoids mistakes caused by spelling, quoting, or localized names.

Reset a password and control account state

$newPassword = Read-Host -Prompt 'Enter a new temporary password' -AsSecureString
$account = Get-LocalUser -Name 'PSLabStudent'
$account | Set-LocalUser -Password $newPassword -WhatIf

$account | Disable-LocalUser -WhatIf
$account | Enable-LocalUser -WhatIf

After an actual change, query the account again instead of assuming that the command succeeded.

Get-LocalUser -Name 'PSLabStudent' |
    Select-Object Name, Enabled, PasswordLastSet, Description

Remove a lab account

Removal is destructive. Verify the exact object, preview, perform the removal only when authorized, and verify absence.

$account = Get-LocalUser -Name 'PSLabStudent'
$account | Remove-LocalUser -WhatIf

Get-LocalUser -Name 'PSLabStudent' -ErrorAction SilentlyContinue

A production workflow should also record who approved the change, what group memberships were removed, and whether data ownership must be transferred.

Design an idempotent account script

An idempotent script can be run repeatedly without creating duplicate objects or producing a different result after the desired state is reached.

$name = 'PSLabStudent'
$existingUser = Get-LocalUser -Name $name -ErrorAction SilentlyContinue

if ($null -eq $existingUser) {
    Write-Output "Account $name would be created."
} else {
    Write-Output "Account $name already exists; no duplicate is required."
}

Reliable account automation checks current state, validates input, supports -WhatIf, returns useful objects, and reports failures without exposing secrets.

Practice and self-check

  1. What is the difference between a local account and a domain account?
Show solution

A local account is stored and managed on one computer. A domain account is managed centrally in Active Directory and can be used on authorized domain resources.

  1. Why is Read-Host -AsSecureString safer than a plain-text password literal?
Show solution

It reads the password without displaying it as ordinary text and returns a SecureString, so the password does not need to be written in the script or command history. It does not replace proper access control or secret handling.

  1. Why can a well-known SID be safer than a built-in group name?
Show solution

The SID identifies the built-in group consistently across Windows display languages, while the group's name can be translated.

  1. Which commands change an account's enabled state?
Show solution

Disable-LocalUser disables an account; Enable-LocalUser enables it. Preview supported changes and verify the account afterward.

  1. What makes an account-management script idempotent?
Show solution

It checks the current state and applies only changes needed to reach the desired state. Running it again does not create duplicates or change an already-correct state.

  1. Which checks should occur before removing an account?
Show solution

Confirm authorization and the exact account and computer, and ensure the account is the disposable one created for the lab. Check group memberships and data ownership, preview removal with -WhatIf, and plan how to verify that the account is absent afterward.

Summary

Local-account automation covers discovery, secure creation, least-privilege membership, password reset, state changes, and removal. Preview changes, use a disposable environment, avoid embedded passwords, pass objects through the pipeline, and verify the resulting state.
