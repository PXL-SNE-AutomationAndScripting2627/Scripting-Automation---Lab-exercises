Hands-on — Variables, objects, and data types

06 - Variables, objects, and data types

Originele pagina openen →

Goal

Store values in well-named variables, inspect and convert data types, work with collections, and combine related values into structured PowerShell objects.

Learning objectives

By the end of this lab, you can:

  • assign and reassign variables using descriptive names;
  • inspect a value's type with GetType();
  • explain dynamic typing and type-constrained variables;
  • cast values deliberately before calculations;
  • manipulate strings, arrays, and hashtables;
  • use a hashtable for parameter splatting;
  • create and query PSCustomObject instances; and
  • recognise common automatic and environment variables.

Prerequisites

  • Complete the variables lesson before starting this lab.
  • Understand object properties and basic pipeline commands.
  • Use PowerShell 7 on your Windows lab computer.

Environment and safety requirements

Use PowerShell 7 and the approved course setup on your Windows lab computer. Administrator rights are not required. These commands inspect values or change variables in the current session; they do not modify system settings or files.

How to work in this lab

For every activity, complete the three steps.

  1. Predict: write or discuss what you think will happen.
  2. Run: enter the command exactly as shown.
  3. Reflect: explain the result in your own words.

Start in a fresh PowerShell 7 session to avoid earlier type constraints. Run the activities in order in the same PowerShell session. Some activities reuse variables created earlier. Activity 4.2 requires Activity 4.1's array; Activity 5.2 requires Activity 5.1's hashtable. If you restart the terminal, recreate the relevant part's values before continuing. Do not assign values to automatic variables such as $HOME.

Keeping data in variables and objects lets later commands reuse it without parsing formatted text.

After attempting each activity, open Show solution to check your commands, expected results, and explanations. The final exercise and self-check also have solutions. Keep the session and setup required by the activity. If you already changed a file or variable, compare its result rather than replaying the change from the solution.

Activity 1.1 — Create and reassign a variable

Predict:

Can the type stored in an unconstrained PowerShell variable change?

Run:

$ticketCount
$ticketCount.GetType().Name

$ticketCount = 'twelve'
$ticketCount
$ticketCount.GetType().Name

Reflect:

  1. What type is stored after the first assignment?
  2. What type is stored after reassignment?
  3. What does this demonstrate about PowerShell's dynamic typing?

Checkpoint: Record both values and their short type names; explain the reassignment.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Solution and explanation:

The prediction is yes: an unconstrained variable can refer to values of another type after reassignment.

  1. The first assignment stores an Int32 value, 12.
  2. The reassignment stores a String, twelve.
  3. This illustrates dynamic typing: the variable is not constrained to one type.

The displayed sequence is 12, Int32, twelve, String.

Activity 4.4 — Store cmdlet results in an array

Collect the running processes so you can count them and inspect one result without running the query again. Get-Process returns process objects; @(...) collects those objects into an array. Run this example directly in the terminal; it does not depend on earlier activity variables.

Predict

Will $runningProcesses contain process names as strings or process objects?

Run:

$runningProcesses = @(Get-Process)

$runningProcesses.GetType().Name
$runningProcesses.Count
$runningProcesses[0].GetType().FullName
$runningProcesses[0] | Select-Object -Property ProcessName, Id

Reflect:

  1. What type does the array report, and how many elements does it contain?
  2. What type is the first element, and which properties do you display?
  3. Why can another student's process count differ from yours?

Checkpoint: Confirm the array type, record its count, and display the first process's name and ID.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Solution and explanation:

The prediction is that the array contains process objects, not just names.

  1. The array type is Object[]. Its count is the number of process objects returned when Get-Process ran.
  2. The first element is a System.Diagnostics.Process object. The final command displays its ProcessName and Id properties.
  3. Computers run different applications and background processes. Processes also start and stop, so counts can differ between students and runs.

@(...) keeps the result as an array even if a query returns only one object or no objects. The process name, ID, and count depend on the computer.

Activity 5.3 — Use a hashtable for splatting

Predict

Which date components does the hashtable supply to the command?

    Year  = 2026

$courseStart.GetType().Name

Reflect:

  1. How do the hashtable keys relate to Get-Date parameters?

  3. Why can splatting improve readability?

Checkpoint: Identify the named arguments and distinguish supplied date parts from defaults.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Solution and explanation:

The keys match the -Year, -Month, and -Day parameter names. @dateParameters splats the pairs into the command as named arguments. The result is a DateTime for 21 September 2026. Splatting separates data from the command and makes long calls easier to read and edit.

Only the calendar date is fixed. Unspecified time components come from the current time, and the display format varies with the host and culture.

Part 7 — Challenge: build a typed course summary

Filename: Get-CourseSummary.ps1

Save the supplied data and your challenge commands in this file. Run . .\Get-CourseSummary.ps1 in your lab session.

Scenario

An instructor wants a reusable object that summarises a course and its submitted results.

Your task

Create the following data:

$courseInfo = @{
    Name    = 'Automation and Scripting'
    Credits = 6
    Active  = $true
}

$results = @(
    [pscustomobject]@{ Student = 'Alex';   Score = 82; Submitted = $true  }
    [pscustomobject]@{ Student = 'Morgan'; Score = 74; Submitted = $false }
    [pscustomobject]@{ Student = 'Sam';    Score = 91; Submitted = $true  }
)

Use @(...) around the filtered pipeline to keep submitted results as an array, even if only one result matches.

Then:

  1. verify that Credits and every Score are numeric;
  2. select only submitted results;
  3. calculate the average submitted score;
  4. create $courseSummary as a PSCustomObject with Course, Credits, Active, StudentCount, SubmittedCount, and AverageScore;
  5. display the summary and inspect its members; and
  6. explain why a custom object is more reusable than one formatted text line.

Success criteria: The summary contains the six requested properties. Counts are calculated from the supplied collection, numeric and Boolean values retain their types, and the average uses only submitted results.

# Select submitted results here.

# Calculate the average here.

# Create the summary object here.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Course-summary solution (Beginner):

$courseInfo = @{
    Name    = 'Automation and Scripting'
    Credits = 6
    Active  = $true
}

$results = @(
    [pscustomobject]@{ Student = 'Alex'; Score = 82; Submitted = $true }
    [pscustomobject]@{ Student = 'Morgan'; Score = 74; Submitted = $false }
    [pscustomobject]@{ Student = 'Sam'; Score = 91; Submitted = $true }
)

$submittedResults = @($results | Where-Object Submitted -eq $true)
$averageSubmittedScore = (
    $submittedResults | Measure-Object -Property Score -Average
).Average

$courseSummary = [pscustomobject]@{
    Course         = $courseInfo.Name
    Credits        = $courseInfo.Credits
    Active         = $courseInfo.Active
    StudentCount   = $results.Count
    SubmittedCount = $submittedResults.Count
    AverageScore   = $averageSubmittedScore
}

$courseSummary
$courseInfo.Credits.GetType().Name
$results.Score | ForEach-Object { $_.GetType().Name }
$courseSummary | Get-Member

The custom object keeps each value as a named property, so it can be inspected, filtered, sorted, or exported instead of being trapped in one formatted text line.

Expected summary: Course = Automation and Scripting, Credits = 6, Active = True, StudentCount = 3, SubmittedCount = 2, and AverageScore = 86.5. Alex and Sam are submitted. Credits and input scores report Int32; the calculated average is Double.

Show solution Optimized

Course-summary solution (Optimized):

$courseInfo = @{
    Name    = 'Automation and Scripting'
    Credits = 6
    Active  = $true
}

$results = @(
    [pscustomobject]@{ Student = 'Alex'; Score = 82; Submitted = $true }
    [pscustomobject]@{ Student = 'Morgan'; Score = 74; Submitted = $false }
    [pscustomobject]@{ Student = 'Sam'; Score = 91; Submitted = $true }
)

$submittedResults = @($results | Where-Object Submitted)
$statsSubmitted = $submittedResults | Measure-Object -Property Score -Average

$courseSummary = [pscustomobject][ordered]@{
    Course         = $courseInfo.Name
    Credits        = $courseInfo.Credits
    Active         = $courseInfo.Active
    StudentCount   = $results.Count
    SubmittedCount = $submittedResults.Count
    AverageScore   = $statsSubmitted.Average
}

$courseSummary
@($courseInfo.Credits, $results.Score) | ForEach-Object { $_.GetType().Name }

The optimized version combines the filtering condition to just Submitted since it's a Boolean property, uses [ordered] to preserve property display order, and assigns the measurement result directly rather than accessing a nested property. Both versions produce the same summary with identical property values and types.

Self-check answers:

  1. Call .GetType(), or .GetType().Name for the short type name. Do not call a method on $null; check whether a value exists first.
  2. An unconstrained variable can reference values of different types after reassignment.
  3. A cast such as [int]'10' converts a value. A declaration such as [int]$count = 10 also constrains later assignments to that variable.
  4. No. $null is absence of a value; an empty string is a string of length zero.
  5. 0 selects the first element; -1 selects the last.
  6. Arrays store ordered, indexed values. Hashtables map keys to values.
  7. In this lab, a hashtable's keys and values supply named command arguments when used as @dateParameters.
  8. Custom objects expose named properties that pipeline and export commands can process directly while retaining their data types.

Summary

Variables give names to values and object references. PowerShell usually determines types dynamically, while casts and type constraints let a script require specific data. Arrays store ordered values, hashtables store key-value pairs, and PSCustomObject combines named properties into pipeline-friendly records.
