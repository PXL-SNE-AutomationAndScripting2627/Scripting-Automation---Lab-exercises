Hands-on — Functions

12 - Functions

Originele pagina openen →

Goal

Turn tested PowerShell logic into reusable, discoverable functions that accept parameters and return objects.

Learning objectives

By the end of this lab, you can:

  • define and call a function using an approved verb-noun name;
  • add typed, validated, and default parameters;
  • use [CmdletBinding()] and Write-Verbose;
  • return pipeline-friendly values and custom objects;
  • accept pipeline input in a process block; and
  • explain local function scope.

Prerequisites

  • Complete Functions before starting this lab.
  • Complete 11 — Exception handling.
  • Understand parameters, conditions, loops, and custom objects.

How to work in this lab

Define each function in the current session, test it immediately, and inspect its command metadata.

After attempting each activity, open Show solution to check your commands, expected results, and explanations. The final exercise and self-check also have solutions. Keep the session and setup required by the activity. If you already changed a file or variable, compare its result rather than replaying the change from the solution.

Part 2 — Build an advanced function

Activity 2.1 — Add cmdlet binding and validation

function ConvertTo-GradeLabel {
    [CmdletBinding()]
    param(
        [Parameter(Mandatory)]
        [ValidateRange(0, 100)]
        [int]$Score
    )

    Write-Verbose "Classifying score $Score"

    if ($Score -ge 85) {
        'Distinction'
    } elseif ($Score -ge 50) {
        'Pass'
    } else {
        'Fail'
    }
}

ConvertTo-GradeLabel -Score 78
ConvertTo-GradeLabel -Score 92 -Verbose

Reflect

  1. What capability does [CmdletBinding()] add here?
  2. Which input range is accepted?
  3. Does verbose text become part of the success output?

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results and reflection answers:

[CmdletBinding()] supplies common parameters including -Verbose. Validation accepts 0 through 100. Verbose stream output is separate from success output.

The labels are Pass for 78 and Distinction for 92. The second call additionally displays the verbose classification message.

Activity 2.2 — Return a custom object

function Get-ScoreAssessment {
    [CmdletBinding()]
    param(
        [Parameter(Mandatory)]
        [ValidateRange(0, 100)]
        [int]$Score
    )

    [pscustomobject]@{
        Score = $Score
        Label = ConvertTo-GradeLabel -Score $Score
        Passed = $Score -ge 50
    }
}

Get-ScoreAssessment -Score 78
Get-ScoreAssessment -Score 78 | Get-Member

Reflect

  1. Which properties are returned?
  2. Why is object output easier to filter and export than a coloured message?

Show solution

Expected results and reflection answers:

The object has Score, Label, and Boolean Passed. Consumers can filter or export named properties without parsing display text.

For 78, the properties are Score = 78, Label = Pass, and Passed = True.

Part 3 — Accept pipeline input

Activity 3.1 — Process every pipeline value

function Get-NumberAssessment {
    [CmdletBinding()]
    param(
        [Parameter(Mandatory, ValueFromPipeline)]
        [int]$Number
    )

    process {
        [pscustomobject]@{
            Number = $Number
            Even   = $Number % 2 -eq 0
            Square = $Number * $Number
        }
    }
}

1..4 | Get-NumberAssessment

Reflect

  2. Why is the process block required for each input object?
  3. How many objects are returned?

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results and reflection answers:

ValueFromPipeline binds each incoming integer to Number. process runs once per incoming item and returns four objects.

The numbers 1 through 4 have squares 1, 4, 9, and 16. Even is False, True, False, and True, respectively. A process block ensures that the calculation runs for each incoming object.

Device-assessment solution (Beginner):

function Get-DeviceAssessment {
    [CmdletBinding()]
    param(
        [Parameter(Mandatory, ValueFromPipeline)]
        [psobject]$InputObject,

        [ValidateRange(1, 1000)]
        [int]$MinimumFreeGB = 15
    )

    process {
        Write-Verbose "Assessing $($InputObject.Name)"

        if ($InputObject.State -ne 'Online') {
            $ready = $false
            $reason = 'Offline'
        } elseif (-not $InputObject.Updated) {
            $ready = $false
            $reason = 'Updates required'
        } elseif ($InputObject.FreeGB -lt $MinimumFreeGB) {
            $ready = $false
            $reason = 'Insufficient free space'
        } else {
            $ready = $true
            $reason = 'Ready'
        }

        [pscustomobject]@{
            Name   = $InputObject.Name
            Ready  = $ready
            Reason = $reason
        }
    }
}

$assessments = $devices | Get-DeviceAssessment -Verbose
$assessments
$assessments | Where-Object Ready

Only LT-204 is ready. The function reads input properties and creates new output objects; it assigns nothing to the input objects.

Show solution Optimized

Use the challenge's supplied input objects in the same session.

Device-assessment solution (Optimized):


function Get-DeviceAssessment {
    [CmdletBinding()]
    param(
        [Parameter(Mandatory, ValueFromPipeline)]
        [psobject]$InputObject,

        [ValidateRange(1, 1000)]
        [int]$MinimumFreeGB = 15
    )

    process {
        Write-Verbose "Assessing $($InputObject.Name)"

        $reason = switch ($true) {
            ($InputObject.State -ne 'Online') {
                'Offline'
                break
            }
            (-not $InputObject.Updated) {
                'Updates required'
                break
            }
            ($InputObject.FreeGB -lt $MinimumFreeGB) {
                'Insufficient free space'
                break
            }
            default {
                'Ready'
            }
        }

        [pscustomobject]@{
            Name   = $InputObject.Name
            # Ready is true only if the reason is 'Ready', defaulting to false otherwise
            Ready  = $reason -eq 'Ready'
            Reason = $reason
        }
    }
}

# Create test devices
$devices = @(
    [pscustomobject]@{ Name = 'LT-204'; State = 'Online';  Updated = $true;  FreeGB = 24 }
    [pscustomobject]@{ Name = 'LT-205'; State = 'Online';  Updated = $false; FreeGB = 30 }
    [pscustomobject]@{ Name = 'DT-301'; State = 'Online';  Updated = $true;  FreeGB = 8 }
    [pscustomobject]@{ Name = 'DT-302'; State = 'Offline'; Updated = $true;  FreeGB = 40 }
)

# Assess all devices
$assessments = $devices | Get-DeviceAssessment -Verbose

# Display all results
$assessments

# Display only ready devices
$assessments | Where-Object Ready

The optimized version uses a switch statement with -true matching to determine the reason in one expression, reducing the number of conditional branches. This approach is more concise and scales better when adding new readiness criteria. Both versions produce identical results.

Summary

Functions package one responsibility behind a discoverable command name. Parameters define the interface, local scope protects internal state, and object output makes functions compose naturally in pipelines.
