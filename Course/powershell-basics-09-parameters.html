09 - Parameters

Originele pagina openen →

Learning objectives

By the end of this chapter, you can:

  • Distinguish parameters from the argument values supplied to them.
  • Define named, positional, typed, array, switch, and mandatory parameters.
  • Use default values and validation attributes.
  • Explain where to place [CmdletBinding()] and what it enables.
  • Distinguish a supplied parameter from its current value.
  • Inspect a script's parameter syntax with Get-Command and Get-Help.

Prerequisites

  • Complete the variables chapter.
  • Be able to create, save, inspect, and run a small PowerShell script.
  • PowerShell 7 and a code editor such as Visual Studio Code.
  • Instructor-prepared writable access to C:\powershell.

Why parameters matter

Parameters let you reuse a script with different inputs without editing its source. For example, a file report can accept a folder path instead of always inspecting the same hard-coded folder.

A parameter is a named input declared by a command. An argument is the value supplied for that input. In this command, Name is the parameter and explorer is its argument:

Get-Process -Name explorer

This command lists matching processes if Explorer is running. It does not start a process.

Parameter and argument

flowchart LR
    A["Command: Get-Process"] --> B["Parameter: -Name"]
    B --> C["Argument: explorer"]
    C --> D["Find matching process objects"]

The parameter identifies the input; the argument supplies its value.

Prepare the lesson workspace

Your instructor must prepare C:\powershell with writable access. Save the chapter's example scripts in their own folder, separate from the hands-on:

$parametersLessonRoot = Join-Path -Path 'C:\powershell' -ChildPath 'Parameters-Lesson'
New-Item -Path $parametersLessonRoot -ItemType Directory -Force | Out-Null
Set-Location -LiteralPath $parametersLessonRoot
Get-Location

The current location should be C:\powershell\Parameters-Lesson. When a section says Save as, create that file in Visual Studio Code, paste the complete script block, and save it. Run the following calls in the terminal from this folder. Replace only the file named by the section; keep other examples for comparison. Do not put the terminal calls in the file.

If you restart the terminal, run this folder setup again. The files remain on disk, but session variables and the current location may differ. Keep the files for review; no deletion is required.

The foundational sequence follows the guided lab. Sections labelled Advanced develop array inputs, binding control, presence checks, and previews after the basic examples; advanced describes depth.

Named and positional parameters

A named argument uses a hyphen before the parameter name, followed by its value:

Get-Process -Name explorer

A positional argument omits the name. PowerShell uses the parameter's defined position to bind the value:

Get-Process explorer

Both commands bind explorer to Name. Named parameters make scripts easier to review. Positional parameters are useful for short interactive commands when the meaning is clear.

To inspect the syntax and position of a parameter, use:

Get-Command Get-Process -Syntax
Get-Help Get-Process -Parameter Name

Apply: Activity 1.1: a named input and Activity 8.1: positional calls.

The parameter block

A param() block declares the inputs accepted by a script or function. Save this example as Named_Parameters_Example_1.ps1:

param(
    [string]$FirstName,
    [string]$LastName,
    [string]$Greeting = 'Hello'
)

Write-Output "$Greeting, $FirstName $LastName!"

The declaration has three parts:

  • The type, such as [string], describes the value expected by the parameter.
  • The variable name, such as $FirstName, becomes the parameter name used by callers.
  • An assignment, such as = 'Hello', supplies a default value when the argument is omitted.

Follow these rules:

  • Place the script's param() block before executable statements. Comments, blank lines, #requires directives, and script attributes can precede it.
  • Inside a function, place the block at the start of the function body, after any comments and function attributes.
  • Separate parameter declarations with commas. Do not add a comma after the last parameter.
  • Blank lines inside the block are allowed and can improve readability.
  • Place [Parameter(...)] and validation attributes directly before the parameter they describe.
  • Place [CmdletBinding()] before param(), outside its parentheses.

After saving a parameter definition, inspect how callers can use it. Run Get-Command .\the_script.ps1 -Syntax, replacing the_script.ps1 with your saved filename. For this example, run in the terminal:

Get-Command .\Named_Parameters_Example_1.ps1 -Syntax

The syntax line is:

.\Named_Parameters_Example_1.ps1 [[-FirstName] <string>] [[-LastName] <string>] [[-Greeting] <string>]
  • <string> means supply a text value; do not type the angle brackets.
  • The outer brackets in [[-FirstName] <string>] mean the whole input is optional. All three inputs are optional in this version.
  • The inner brackets around -FirstName mean the name can be omitted when supplying the value positionally.

Get-Command -Syntax reads the saved parameter declarations without running the script body. It does not show default values such as 'Hello'; inspect param() for those. Save and rerun the command after changing declarations. PowerShell may also show a resolved-path header above the syntax line.

These two calls supply the same named values in different orders:

.\Named_Parameters_Example_1.ps1 -FirstName Dominique `
    -LastName Houbrechts -Greeting Welcome
.\Named_Parameters_Example_1.ps1 -Greeting Welcome `
    -LastName Houbrechts -FirstName Dominique

Each call produces:

Welcome, Dominique Houbrechts!

This simple script also accepts positional values in declaration order:

.\Named_Parameters_Example_1.ps1 Dominique Houbrechts Welcome

Later in this chapter, you will control positional binding explicitly.

Apply: Activities 2.1–3.1: create a script and add an input.

Default values

A default value is used when the caller omits an optional parameter. A supplied value replaces that default.

Save as DeclareParametersDefaultValue.ps1:

param(
    [int]$Amount = 10
)

Write-Output $Amount

.\DeclareParametersDefaultValue.ps1

10

.\DeclareParametersDefaultValue.ps1 -Amount 20

20

Parameters are optional unless marked mandatory, even if they have no explicit default. A default assignment does not cancel [Parameter(Mandatory)]; avoid combining them for a required input.

Apply: Activity 3.2: use and override a default.

Data types and arrays

A type declaration tells PowerShell which type to bind. PowerShell attempts to convert supplied values to that type and rejects values it cannot convert.

Type Purpose Example argument
[string] Text -FirstName Dominique
[int] Whole numbers -Age 25
[double] Floating-point numbers -Size 2.5
[bool] An explicit Boolean value -Enabled $true
[datetime] A date and time -Date '2026-10-09'
[string[]] An array of strings -Names 'Alex', 'Sam'
[int[]] An array of integers -Numbers 2, 3, 4, 5
[switch] An option enabled by its name -Capital

Type conversion checks whether a value can become the required type. It does not check every business rule. For example, an integer type alone does not prevent a negative age.

Save as DeclareParametersDataTypes.ps1:

param(
    [string]$FirstName,
    [int]$Age
)

Write-Output "First name: $FirstName"
Write-Output "Age: $Age"
Write-Output $FirstName.GetType().Name
Write-Output $Age.GetType().Name

.\DeclareParametersDataTypes.ps1 -FirstName Dominique -Age 25

First name: Dominique
Age: 25
String
Int32

Passing -Age twenty produces a conversion error before the body runs.

Advanced: array parameters

Use a typed array when all elements should have the same type. [array] accepts mixed element types; [int[]] requires elements convertible to integers.

Save as DeclareParametersArray.ps1:

param(
    [int[]]$Numbers = @()
)

Write-Output "Total numbers are: $($Numbers.Count)"
foreach ($number in $Numbers) {
    Write-Output $number
}
Write-Output $Numbers.GetType().Name

.\DeclareParametersArray.ps1 -Numbers 2, 3, 4, 5

Total numbers are: 4
2
3
4
5
Int32[]

These examples are called from a PowerShell session. Passing arrays through a separate pwsh -File process involves command-line argument handling and is not equivalent to the calls shown here.

Apply: Activity 4.1: integer input and conversion errors. Array inputs extend this binding idea; the guided lab keeps scalar inputs.

Mandatory parameters

A mandatory parameter requires input. In an interactive session, PowerShell prompts for an omitted value. When prompting is unavailable, such as with pwsh -NonInteractive, missing mandatory input produces an error.

[Parameter(Mandatory)] and [Parameter(Mandatory = $true)] are equivalent. Save this example as DeclareParametersMandatory.ps1:

[CmdletBinding()]
param(
    [Parameter(Mandatory)]
    [string]$Username,

    [string]$FullName
)

Write-Output "Username: $Username"
Write-Output "Full name: $FullName"

Inspect the saved definition before running it:

Get-Command .\DeclareParametersMandatory.ps1 -Syntax

The syntax line is:

.\DeclareParametersMandatory.ps1 [-Username] <string> [[-FullName] <string>] [<CommonParameters>]

[-Username] <string> has no outer brackets around the complete input, so a username value is required. Only the name is optional for a positional call. FullName remains optional. [<CommonParameters>] represents built-in options such as -Verbose, enabled here by [CmdletBinding()]. You will use verbose output later in this chapter.

.\DeclareParametersMandatory.ps1 -Username dhoubrechts -FullName 'Dominique Houbrechts'

Username: dhoubrechts
Full name: Dominique Houbrechts

Run the following interactively and enter dhoubrechts when prompted:

.\DeclareParametersMandatory.ps1

The script then reports that username and an empty full name. The prompt's wording can vary between PowerShell versions and hosts.

Apply: Activity 4.2: mandatory input in a terminal.

Validation

Validation attributes restrict the values accepted by a parameter before the script body runs. Use them to reject invalid input with a useful error.

Attribute Use
[ValidateSet(...)] Allow only listed values.
[ValidatePattern(...)] Require a regular expression match.
[ValidateRange(...)] Require a value within an inclusive range.
[ValidateScript({...})] Apply a custom test to each supplied value.
[ValidateNotNullOrEmpty()] Reject null or empty input.

An inclusive range

Save as DeclareParameterValidateRange.ps1:

param(
    [Parameter(Mandatory)]
    [ValidateRange(1, 100)]
    [int]$Number
)

Write-Output $Number

.\DeclareParameterValidateRange.ps1 -Number 100

100

-Number 110 fails. This range includes 1 and 100; the custom test below uses a different boundary rule.

A fixed set of values

Use a fixed set when a script supports only a few known report categories. Save as DeclareParameterValidate.ps1:

param(
    [ValidateSet('Backup', 'Inventory', 'Health',
        ErrorMessage = 'Report kind {0} is not in the allowed set: {1}.')]
    [string]$ReportKind = 'Inventory'
)

Write-Output "Report kind: $ReportKind"

.\DeclareParameterValidate.ps1
.\DeclareParameterValidate.ps1 -ReportKind Backup

Report kind: Inventory
Report kind: Backup

-ReportKind Finance fails validation. ValidateSet is case-insensitive by default. In the custom error message, {0} is the supplied value and {1} is the allowed set. Custom ErrorMessage properties used in this chapter require PowerShell 6 or later.

Advanced: a regular expression pattern

A regular expression describes a text pattern. Here, \A and \z require the complete input, [0-9] represents an ASCII digit, and {3} requires three repetitions. These strict anchors also reject a trailing newline; $ can match just before a final newline.

Save as DeclareParameterValidatePattern.ps1:

param(
    [Parameter(Mandatory)]
    [ValidatePattern('\ALAB-[0-9]{3}\z', ErrorMessage = '{0} must use the format LAB-001.')]
    [string]$AssetCode
)

Write-Output $AssetCode

.\DeclareParameterValidatePattern.ps1 -AssetCode LAB-001

LAB-001

-AssetCode LAB-01 fails validation. This checks the format; it does not prove that the asset exists.

ValidatePattern is case-insensitive by default, so lab-001 also passes this example. Pattern matching does not normalise the supplied text.

Advanced: a custom validation script

Within ValidateScript, $_ is the value being checked. Return $true for valid input; $false or a thrown error rejects it. Array parameters are checked element by element.

Save as DeclareParameterValidateScript.ps1:

param(
    [Parameter(Mandatory)]
    [ValidateScript({ $_ -gt 0 -and $_ -lt 100 })]
    [int]$Number
)

Write-Output $Number

.\DeclareParameterValidateScript.ps1 -Number 50

50

-Number 0, -Number 100, and -Number 110 fail because this rule excludes both boundaries.

Validation attributes check supplied arguments, not default assignments. Choose valid defaults yourself. On an optional parameter, validation alone does not require the caller to provide input; add Mandatory when omission must be prevented.

Apply: Activities 5.1–5.2: range and fixed choices. The pattern and custom-script examples develop more detailed validation rules.

Switch parameters

Declare an option with [switch]. Without an explicit default, an omitted switch is false. Its name alone enables it. Use [bool] when callers should supply a separate Boolean value.

Save as DeclareParametersSwitch.ps1:

[CmdletBinding()]
param(
    [Parameter(Mandatory)]
    [string]$FirstName,

    [switch]$Capital
)

if ($Capital) {
    $FirstName = $FirstName.ToUpper()
}

Write-Output "First name: $FirstName"

.\DeclareParametersSwitch.ps1 -FirstName dominique

First name: dominique

.\DeclareParametersSwitch.ps1 -FirstName dominique -Capital

First name: DOMINIQUE

A caller can explicitly disable a switch using a colon:

.\DeclareParametersSwitch.ps1 -FirstName dominique -Capital:$false

First name: dominique

Use if ($Capital) or $Capital.IsPresent to test its Boolean value. IsPresent is false for -Capital:$false, even though the caller supplied the parameter. Do not use -Capital $false; the separate value is treated as another argument.

Apply: Activity 6.1: switch values, including explicit false.

Using [CmdletBinding()]

Use [CmdletBinding()] when a reusable script or function needs cmdlet-style parameter handling. A function with this attribute is an advanced function. A script can use the same attribute before its top-level param() block.

Save this example as Show-FolderPath.ps1:

[CmdletBinding()]
param(
    [string]$Path = '.'
)

Write-Verbose "Resolving folder path: $Path"
Resolve-Path -LiteralPath $Path

Compare these calls:

.\Show-FolderPath.ps1 -Path .
.\Show-FolderPath.ps1 -Path . -Verbose
Get-Command .\Show-FolderPath.ps1 -Syntax
Show solution

Both runs return the resolved path. -Verbose also displays the diagnostic message. The actual path depends on your current folder. The syntax query shows declared and common parameters; it does not run the script.

[CmdletBinding()] enables common parameters, including -Verbose, -Debug, and -ErrorAction, and provides $PSCmdlet for advanced methods. Unknown parameter names and unmatched positional arguments fail during binding. Do not declare your own parameters with common-parameter names.

[Parameter(...)] configures one input, such as making it mandatory. It can also make a function advanced without [CmdletBinding()]. Using both makes their different purposes explicit.

Apply: Activity 7.1: request diagnostic output.

Explicit positional parameters

Use Position to define which parameter receives each unnamed argument. Positions start at 0. An explicit position takes precedence over PositionalBinding = $false.

Save as Greet-User.ps1:

[CmdletBinding(PositionalBinding = $false)]
param(
    [Parameter(Position = 0, Mandatory)]
    [string]$FirstName,

    [Parameter(Position = 1, Mandatory)]
    [string]$LastName,

    [Parameter(Position = 2)]
    [string]$Greeting = 'Hello'
)

Write-Output "$Greeting, $FirstName $LastName!"

.\Greet-User.ps1 Dominique Houbrechts Welcome

Welcome, Dominique Houbrechts!

Omitting the optional greeting uses its default:

.\Greet-User.ps1 Dominique Houbrechts

Hello, Dominique Houbrechts!

Named arguments still work:

.\Greet-User.ps1 -FirstName John -LastName Doe -Greeting 'Good morning'

Good morning, John Doe!

Mandatory controls whether input is required. Position controls whether callers may omit the parameter name. ParameterSetName groups valid combinations of inputs; it does not assign a position or directly require a parameter name.

Apply: Activity 8.1: compare named and positional calls.

Advanced: unnamed arguments with $args

$args contains arguments that were not bound to declared parameters in a simple script or function. It is an array, and its first element has index 0. Reading $args[0] is different from declaring a positional parameter in param().

Save this example as Unnamed_Arguments_Example_1.ps1:

$argument1 = $args[0]
$argument2 = $args[1]
$argument3 = $args[2]

Write-Host $argument1 $argument2 $argument3

Run it from the folder containing the file:

.\Unnamed_Arguments_Example_1.ps1 one two three

Expected output:

one two three

A second example, Unnamed_Arguments_Example_2.ps1, inspects every argument:

Write-Output "There are a total of $($args.Count) arguments"
for ($index = 0; $index -lt $args.Count; $index++) {
    Write-Output "Argument $index is $($args[$index])"
}

.\Unnamed_Arguments_Example_2.ps1 one two three four

There are a total of 4 arguments
Argument 0 is one
Argument 1 is two
Argument 2 is three
Argument 3 is four

For reusable scripts, prefer declared parameters. They provide meaningful names, types, help information, and validation. Advanced scripts and functions reject unmatched arguments rather than collecting them in $args.

Checking whether a parameter was supplied

Advanced depth: distinguish binding from the resulting value.

A parameter's presence and its value answer different questions. Use $PSBoundParameters.ContainsKey('Name') to check binding. Use the parameter variable to check its value.

$PSBoundParameters is a dictionary of parameters bound in the current script or function. It includes named and positional arguments, but does not include an optional parameter merely because it has a default value.

Save as CheckParameterContainsKey.ps1:

[CmdletBinding()]
param(
    [string]$Parameter1 = 'Default',
    [switch]$Parameter2
)

$parameter1Supplied = $PSBoundParameters.ContainsKey('Parameter1')
Write-Output "Parameter1 supplied: $parameter1Supplied"
Write-Output "Parameter1 value: $Parameter1"
$parameter2Supplied = $PSBoundParameters.ContainsKey('Parameter2')
Write-Output "Parameter2 supplied: $parameter2Supplied"
Write-Output "Parameter2 enabled: $($Parameter2.IsPresent)"

.\CheckParameterContainsKey.ps1

Parameter1 supplied: False
Parameter1 value: Default
Parameter2 supplied: False
Parameter2 enabled: False

.\CheckParameterContainsKey.ps1 -Parameter1 Value1 -Parameter2:$false

Parameter1 supplied: True
Parameter1 value: Value1
Parameter2 supplied: True
Parameter2 enabled: False

Why $null and truth tests are different

A null comparison checks the current value, not whether the caller supplied an argument. An untyped parameter without a default can be null because it was omitted or because the caller explicitly supplied $null.

Save as CheckParameterContainsNull.ps1:

param(
    $Parameter1
)

$parameter1Supplied = $PSBoundParameters.ContainsKey('Parameter1')
Write-Output "Parameter1 supplied: $parameter1Supplied"
Write-Output "Parameter1 is null: $($null -eq $Parameter1)"

.\CheckParameterContainsNull.ps1 -Parameter1 $null

Parameter1 supplied: True
Parameter1 is null: True

Typed parameters have their own conversion and default behavior. For example, an optional [int] without an explicit default is 0, and an optional [switch] is false.

Likewise, if ($Parameter1) tests truthiness. Values such as 0, $false, an empty string, and $null evaluate to false even when supplied. For switches, test the value to decide whether to enable the feature; use ContainsKey() only when you need to know whether the caller supplied it.

Advanced: controlling positional binding

[CmdletBinding()] permits automatic positional binding by default. Set PositionalBinding = $false to require names unless a parameter has an explicit Position attribute:

[CmdletBinding(PositionalBinding = $false)]
param(
    [string]$Greeting = 'Hello'
)

Write-Output $Greeting

If saved as Show-Greeting.ps1, use -Greeting Welcome. Passing only Welcome fails because no parameter accepts a positional value.

Advanced: supporting -WhatIf and -Confirm

For scripts or functions that change state, SupportsShouldProcess = $true adds -WhatIf and -Confirm. Guard each change with $PSCmdlet.ShouldProcess() so previews and confirmations work.

Paste this function into your lab session:

function New-CourseNote {
    [CmdletBinding(SupportsShouldProcess = $true)]
    param(
        [Parameter(Mandatory)]
        [ValidateNotNullOrEmpty()]
        [string]$Path
    )

    if ($PSCmdlet.ShouldProcess($Path, 'Create a course note')) {
        New-Item -Path $Path -ItemType File -Value 'Course note' -ErrorAction Stop
    }
}

Preview it from your personal lab folder:

New-CourseNote -Path .\course-note.txt -WhatIf

The preview describes the proposed action without creating a file. [CmdletBinding()] alone does not add these two parameters.

Use these questions to inspect the advanced examples in this chapter:

  1. How does reading $args[0] differ from declaring [Parameter(Position = 0)]?
Show solution

$args[0] reads the first unbound argument in a simple script or function. It has no declared parameter name, type constraint, or validation attribute. A declared positional parameter participates in binding and can have a type, validation, help, and a meaningful name. It also accepts its named form. Advanced scripts reject unmatched arguments rather than collecting them.

  1. Which values among 0, 1, 99, and 100 pass the custom numeric test and the inclusive range? Check their respective scripts.
Show solution
Value ValidateScript: greater than 0 and less than 100 ValidateRange(1, 100)
0 Reject Reject
1 Accept Accept
99 Accept Accept
100 Reject Accept

The custom test excludes both 0 and 100. The range includes both 1 and 100.

  1. Use CheckParameterContainsKey.ps1 to compare an omitted input, an explicit default value, and an explicitly false switch.
Show solution

Run from the folder where you saved the chapter's script:

.\CheckParameterContainsKey.ps1
.\CheckParameterContainsKey.ps1 -Parameter1 Default
.\CheckParameterContainsKey.ps1 -Parameter2:$false

With no arguments, both supplied checks are False; Parameter1 is Default and Parameter2 is disabled. Supplying -Parameter1 Default makes its supplied check True while keeping the same value. Supplying -Parameter2:$false makes that switch's supplied check True while its enabled value remains False. Presence and value answer different questions.

  1. Why does a null check not prove whether an argument was supplied?
Show solution

A null check inspects the current value. An untyped input can be null because it was omitted or because the caller supplied $null explicitly. A default can also provide a non-null value when no argument was supplied. Use $PSBoundParameters.ContainsKey('Parameter1') to check binding.

  1. Why must a script guard its changes with ShouldProcess() after adding SupportsShouldProcess? Verify that the preview creates no file.
Show solution

SupportsShouldProcess exposes -WhatIf and -Confirm. The script must call $PSCmdlet.ShouldProcess(...) and perform its mutation only when that call returns True. With -WhatIf it returns False, so the protected change is skipped.

After defining New-CourseNote, use a missing path inside your lab folder:

Test-Path -LiteralPath '.\course-note.txt'
New-CourseNote -Path '.\course-note.txt' -WhatIf
Test-Path -LiteralPath '.\course-note.txt'

Both checks should be False. If the first check is True, preserve that file and choose another new filename before previewing. A pre-existing file cannot prove whether the preview created anything. Do not perform an unguarded write after the conditional block.

Summary

Declare inputs in param() and prefer named arguments for clarity. Use types for conversion, validation for permitted values, defaults for optional inputs, and Mandatory for required input. Declare positions explicitly when callers should be able to omit names.

Place [CmdletBinding()] before param() to enable cmdlet-style handling. Use $PSBoundParameters to check whether an input was supplied, and the variable's value to decide what the script should do.
