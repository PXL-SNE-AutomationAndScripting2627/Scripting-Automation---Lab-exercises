Hands-on — Piping, filtering, sorting, grouping, and measuring

03 - Piping, filtering, sorting, grouping, and measuring

Originele pagina openen →

Goal

Build PowerShell pipelines that turn a collection of objects into useful information by selecting, filtering, sorting, grouping, and measuring data.

Learning objectives

By the end of this lab, you can:

  • explain how objects move through a multi-stage pipeline;
  • select properties and limit pipeline results;
  • filter objects with comparison, wildcard, and logical operators;
  • sort objects by one or more properties;
  • group objects and interpret group counts; and
  • measure a collection using count, sum, average, minimum, and maximum.

Prerequisites

  • Complete Piping, filtering, sorting, grouping, and measuring before starting this lab.
  • Use PowerShell 7 where available.
  • Understand properties, Get-Member, Select-Object, and Where-Object.

How to work in this lab

For every activity, complete the three steps.

  1. Predict: write or discuss what you think will happen.
  2. Run: enter the command exactly as shown.
  3. Reflect: answer the questions in your own words.

All activities are read-only. The sample data exists only in the current PowerShell session.

After attempting each activity, open Show solution to check your commands, expected results, and explanations. The final exercise and self-check also have solutions. Keep the session and setup required by the activity. If you already changed a file or variable, compare its result rather than replaying the change from the solution.

Part 1 — Prepare and inspect the data

Activity 1.1 — Create a helpdesk dataset

Predict

What kind of object do you expect [pscustomobject] to create?

Run

$tickets = @(
    [pscustomobject]@{ Id = 101; Category = 'Account'; Priority = 2; Status = 'Open';   Minutes = 25 }
    [pscustomobject]@{ Id = 102; Category = 'Network'; Priority = 1; Status = 'Open';   Minutes = 80 }
    [pscustomobject]@{ Id = 103; Category = 'Device';  Priority = 3; Status = 'Closed'; Minutes = 45 }
    [pscustomobject]@{ Id = 104; Category = 'Account'; Priority = 1; Status = 'Closed'; Minutes = 30 }
    [pscustomobject]@{ Id = 105; Category = 'Network'; Priority = 2; Status = 'Open';   Minutes = 60 }
    [pscustomobject]@{ Id = 106; Category = 'Device';  Priority = 2; Status = 'Closed'; Minutes = 20 }
    [pscustomobject]@{ Id = 107; Category = 'Account'; Priority = 3; Status = 'Open';   Minutes = 15 }
    [pscustomobject]@{ Id = 108; Category = 'Network'; Priority = 1; Status = 'Closed'; Minutes = 95 }
)

$tickets

Reflect

  1. How many ticket objects are in the collection?
  2. Which properties does every ticket contain?
  3. Why is structured data more useful than one long line of text?

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results and explanation:

[pscustomobject] creates a structured object with named properties. The collection contains eight objects. Every ticket contains Id, Category, Priority, Status, and Minutes. Structured properties let later commands filter and sort values without parsing display text.

Part 2 — Filter objects

Activity 2.1 — Compare property values

Predict

Which ticket IDs should pass each filter?

Run

$tickets | Where-Object Status -eq 'Open'
$tickets | Where-Object Priority -le 2
$tickets | Where-Object Minutes -gt 60

Reflect

  1. What do -eq, -le, and -gt mean?
  2. Which filter returns tickets 102 and 108?
  3. Why should numeric data such as Minutes be stored as numbers rather than text?

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results and explanation:

-eq means equal to, -le means less than or equal to, and -gt means greater than. Minutes -gt 60 returns IDs 102 and 108. Numbers should be stored as numeric values so comparisons use numeric order; text values can sort or compare lexically instead.

Prediction results: Status -eq 'Open' returns 101, 102, 105, and 107. Priority -le 2 returns 101, 102, 104, 105, 106, and 108. Minutes -gt 60 returns 102 and 108.

Activity 2.2 — Use wildcards and logical operators

Run

$tickets | Where-Object Category -like 'Net*'

$tickets | Where-Object {
    $_.Status -eq 'Open' -and $_.Priority -le 2
}

Reflect

  1. What does * represent in 'Net*'?
  2. What does $_ represent inside the script block?
  3. How does -and affect the result?
  4. Which ticket IDs meet both conditions?

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results and explanation:

* represents zero or more characters, so Net* matches Network. $_ is the current ticket entering Where-Object. -and requires both comparisons to be true. IDs 101, 102, and 105 meet both conditions.

Activity 2.3 — Compare -contains and -in

Run

@('Account', 'Device') -contains 'Device'
'Device' -in @('Account', 'Device')
'Network' -notin @('Account', 'Device')

Reflect

  1. Which operator places the collection on the left?
  2. Which operator places the value on the left?
  3. What Boolean result does each expression return?

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results and explanation:

-contains places the collection on the left and the searched value on the right. -in places the value on the left and collection on the right. All three expressions return True.

Activity 4.2 — Build a compact grouped summary

Run

$tickets |
    Group-Object Status |
    Sort-Object Count -Descending |
    Select-Object Name, Count

Reflect

  1. How many tickets are open and closed?
  2. What object is being sorted after Group-Object?
  3. Why is Name, Count often more useful in a summary than the complete Group property?

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results and explanation:

There are four open and four closed tickets. After Group-Object, the pipeline contains GroupInfo objects, and Sort-Object sorts those by their Count property. A Name, Count summary is compact; the full Group collections are unnecessary when only totals are needed.

The command measures the WorkingSet property, which represents physical memory associated with each process. Results vary because computers run different processes and memory use changes continuously. The pipeline only gets and measures objects; it does not stop or modify processes.

Part 6 — Challenge: create a helpdesk summary

Filename: Get-HelpdeskSummary.ps1

Save both pipelines in this file. After completing Activity 1.1 in the same session, run . .\Get-HelpdeskSummary.ps1 to use its $tickets collection.

Scenario

A helpdesk coordinator needs a read-only report of open, high-priority tickets. In this dataset, priority 1 or 2 is considered high priority.

Your task

Create a pipeline that:

  1. starts with $tickets;
  2. keeps tickets whose status is Open and priority is 2 or lower;
  3. sorts the remaining tickets by Minutes from highest to lowest; and
  4. displays Id, Category, Priority, and Minutes.

Then create a second pipeline that measures the average Minutes for those same tickets.

Explain why the order of filtering, sorting, and selecting matters.

# Write the detailed report pipeline here.

# Write the measurement pipeline here.

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Use $tickets from Activity 1.1 in the same session.

Detailed report solution (Beginner):

$tickets |
    Where-Object { $_.Status -eq 'Open' -and $_.Priority -le 2 } |
    Sort-Object Minutes -Descending |
    Select-Object Id, Category, Priority, Minutes

The expected order is ticket 102 (80), 105 (60), and 101 (25).

Measurement solution (Beginner):

$tickets |
    Where-Object { $_.Status -eq 'Open' -and $_.Priority -le 2 } |
    Measure-Object -Property Minutes -Average

The average is 55. Filtering first ensures both pipelines operate only on relevant tickets. The detailed pipeline sorts complete ticket objects before selecting display properties; measurement uses the numeric Minutes property directly.

Show solution Optimized

Use $tickets from Activity 1.1 in the same session.

Detailed report solution (Optimized):

$highPriorityOpen = { $_.Status -eq 'Open' -and $_.Priority -le 2 }
$tickets | Where-Object $highPriorityOpen | Sort-Object Minutes -Descending | Select-Object Id, Category, Priority, Minutes

Measurement solution (Optimized):

$tickets | Where-Object { $_.Status -eq 'Open' -and $_.Priority -le 2 } | Measure-Object -Property Minutes -Average

The optimized version is identical in functionality but can be condensed on single lines for interactive use. The filter condition could be stored as a script block for reuse across multiple pipelines. Both approaches produce tickets 102 (80), 105 (60), 101 (25) with average of 55.

  5. Which cmdlet collects objects with the same property value?
  6. Which properties can Measure-Object calculate for numeric data?
  7. Why should formatting normally be the final stage of a pipeline?

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Self-check answers:

Question Detailed solution
Which cmdlet filters objects? Where-Object
Which operator means “less than or equal to”? -le
Difference between -contains and -in? -contains has the collection on the left; -in has the value on the left.
Which cmdlet orders objects? Sort-Object
Which cmdlet collects shared property values? Group-Object
Which numeric results can Measure-Object calculate? Count, sum, average, minimum, and maximum; standard deviation is also available when requested.
Why format last? Formatting creates display instructions that are unsuitable for most later object-processing commands.

Summary

A PowerShell pipeline can progressively refine objects. Filter early, sort the remaining objects, select the properties needed by the consumer, and measure or group objects when a summary is required. Keeping objects in the pipeline preserves structured data for later commands.
