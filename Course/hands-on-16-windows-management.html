Hands-on — Windows management

16 - Windows management

Originele pagina openen →

Goal

Combine event, permission, job, and firewall information into a safe Windows management workflow.

Learning objectives

By the end of this lab, you can:

  • discover management and security cmdlets;
  • retrieve a focused set of recent Windows events;
  • inspect an ACL and preview a narrowly scoped rule;
  • manage a complete background-job lifecycle; and
  • build a structured Windows management snapshot.

Prerequisites

  • Complete 15 — Windows information.
  • Complete Automating Windows management before starting this lab.
  • Use PowerShell on Windows.
  • Do not change production ACLs or firewall rules.

How to work in this lab

All system queries are read-only. The ACL activity stops at -WhatIf, and any files are created only in the dedicated lab folder.

Part 1 — Prepare and discover

Activity 1.1 — Create the workspace

$labRoot = Join-Path 'C:\powershell' 'Windows-Management-Lab'
New-Item -Path $labRoot -ItemType Directory -Force

Part 2 — Query recent events

Activity 2.1 — Read a bounded event set

Get-WinEvent -LogName Application -MaxEvents 20 |
    Select-Object TimeCreated, Id, LevelDisplayName, ProviderName

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results: Up to 20 Application events are displayed with their time, ID, level, and provider. Events and counts vary with the computer and access permissions.

Activity 2.2 — Filter warning and error events

$startTime = (Get-Date).AddDays(-1)

$recentProblems = Get-WinEvent -FilterHashtable @{
    LogName   = 'System'
    StartTime = $startTime
    Level     = 2, 3
} -ErrorAction SilentlyContinue

$recentProblems |
    Select-Object TimeCreated, Id, LevelDisplayName, ProviderName

Reflect

  1. Why use -FilterHashtable instead of retrieving the full log?
  2. What do levels 2 and 3 represent?
  3. Why can the result count legitimately be zero?

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results and reflection answers: -FilterHashtable restricts events by log, time, and level during the query instead of retrieving the whole log. Level 2 means error and level 3 warning. No events may match the last day, so zero results are possible. This example suppresses errors; an empty display alone does not prove that the log was queried successfully.

Part 3 — Inspect and preview permissions

Activity 3.1 — Inspect the practice-folder ACL

$acl = Get-Acl -Path $labRoot
$acl | Select-Object Owner, AreAccessRulesProtected
$acl.Access |
    Select-Object IdentityReference, FileSystemRights,
        AccessControlType, IsInherited

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results: The folder's owner and inheritance protection are displayed, followed by its access entries and their identities, rights, allow/deny types, and inherited status. The entries vary by computer.

Activity 3.2 — Build and preview one rule

$identity = [Security.Principal.WindowsIdentity]::GetCurrent().Name
$rule = [Security.AccessControl.FileSystemAccessRule]::new(
    $identity,
    'ReadAndExecute',
    'ContainerInherit,ObjectInherit',
    'None',
    'Allow'
)

$acl.AddAccessRule($rule)
Set-Acl -Path $labRoot -AclObject $acl -WhatIf

Do not remove -WhatIf in this lab.

Reflect

  1. What information does the rule contain?
  2. Why does Set-Acl apply a complete ACL object?
  3. What additional backup and verification would a real ACL change need?

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results and reflection answers: The rule grants the current identity ReadAndExecute, with container and object inheritance, as an allow entry. Set-Acl applies the supplied security descriptor rather than only that entry, so other permissions must be preserved. The preview does not apply the modified ACL. A real authorized change needs a recorded or exported original ACL, a rollback plan, and verification of effective access. Do not remove -WhatIf here.

Part 4 — Manage a background job

Activity 4.1 — Start and monitor

$job = Start-Job -Name 'Lab16Snapshot' -ScriptBlock {
    Get-CimInstance -ClassName Win32_OperatingSystem |
        Select-Object CSName, Caption, Version, LastBootUpTime
}

Get-Job -Name 'Lab16Snapshot'
Wait-Job -Job $job

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results: Start-Job creates a job and returns control while it runs; Get-Job displays its state and Wait-Job waits for it to finish. Check the final state and errors as well as output in the next activity.

Activity 4.2 — Receive, keep, and remove

$firstResult = Receive-Job -Job $job -Keep
$secondResult = Receive-Job -Job $job

$firstResult
$secondResult

Remove-Job -Job $job
Get-Job -Name 'Lab16Snapshot' -ErrorAction SilentlyContinue

Reflect

  1. Why does the prompt return immediately after Start-Job?
  2. What effect does -Keep have?
  3. Why should completed jobs be removed?

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Expected results and reflection answers: The job runs separately, so Start-Job returns the prompt without waiting. -Keep preserves cached output for the second receive. Both variables should contain the same OS result if the job succeeded; values vary by computer. Remove completed jobs to release session resources; the final query should find no such job.

Part 6 — Challenge: create a management snapshot

Filename: Get-WindowsManagementSnapshot.ps1

Create Get-WindowsManagementSnapshot.ps1. It must:

  • use [CmdletBinding()];
  • accept MaxEvents from 1 through 100, defaulting to 10;
  • accept optional OutputPath for JSON;
  • return one object containing computer name, collection time, OS caption, last boot, recent System warning/error count, enabled firewall-rule count, running-service count, and the current user's name;
  • handle an unavailable event log or firewall module without terminating the entire report; and
  • export JSON only after building the object.

Test:

.\Get-WindowsManagementSnapshot.ps1 -MaxEvents 5

$jsonPath = Join-Path $labRoot 'management-snapshot.json'
.\Get-WindowsManagementSnapshot.ps1 -OutputPath $jsonPath
Get-Content -Path $jsonPath -Raw | ConvertFrom-Json

Try the challenge yourself first. Then use the solution to check your work.

Show solution

Student requirements: Create a validated, read-only script that returns the required management properties, records event/firewall query failures, optionally writes JSON, and still outputs its object.

Detailed solution: Use Get-WindowsManagementSnapshot.ps1. Separate try blocks allow unavailable event or firewall data to become explicit error properties while other fields still succeed. A valid query with no matching events is recorded as a count of 0, not as a system failure.

.\Get-WindowsManagementSnapshot.ps1 -MaxEvents 5
$jsonPath = Join-Path $labRoot 'management-snapshot.json'
.\Get-WindowsManagementSnapshot.ps1 -OutputPath $jsonPath
Get-Content -Path $jsonPath -Raw | ConvertFrom-Json
Show solution Optimized

The linked script is the step-by-step version. This alternative keeps the queries separate so an unavailable log or firewall module is reported without losing the rest of the snapshot.

[CmdletBinding()]
param(
    [ValidateRange(1, 100)]
    [int]$MaxEvents = 10,
    [string]$OutputPath
)

if (-not $IsWindows) { throw 'This script requires Windows.' }
$os = Get-CimInstance Win32_OperatingSystem -ErrorAction Stop
$eventError = $null
$firewallError = $null

try {
    $eventCount = @(Get-WinEvent -FilterHashtable @{
        LogName = 'System'; StartTime = (Get-Date).AddDays(-1); Level = 2, 3
    } -MaxEvents $MaxEvents -ErrorAction Stop).Count
} catch {
    if ($_.FullyQualifiedErrorId -like 'NoMatchingEventsFound*') {
        $eventCount = 0
    } else {
        $eventCount = $null
        $eventError = $_.Exception.Message
    }
}

try {
    $firewallCount = @(Get-NetFirewallRule -PolicyStore ActiveStore -ErrorAction Stop |
        Where-Object Enabled -eq 'True').Count
} catch {
    $firewallCount = $null
    $firewallError = $_.Exception.Message
}

$result = [pscustomobject]@{
    ComputerName         = $env:COMPUTERNAME
    CollectedAt          = Get-Date
    OperatingSystem      = $os.Caption
    LastBoot             = $os.LastBootUpTime
    RecentProblemCount   = $eventCount
    EnabledFirewallRules = $firewallCount
    RunningServiceCount  = @(Get-Service -ErrorAction Stop | Where-Object Status -eq 'Running').Count
    CurrentUser          = [Security.Principal.WindowsIdentity]::GetCurrent().Name
    EventQueryError      = $eventError
    FirewallQueryError   = $firewallError
}

if ($OutputPath) {
    $result | ConvertTo-Json | Set-Content -Path $OutputPath -ErrorAction Stop
}
$result

The counts and timestamps depend on the computer and collection time.
